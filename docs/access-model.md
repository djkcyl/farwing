# 统一的身份、授权与连接

状态：已实施（2026-10-16，阶段 1–5 全部完成，见第 7 节的实现记录与验证）。范围：设备身份、谁可以连接本机、用什么证明、怎么连上。目标是五种使用方式（有服务器有账号、有服务器无账号、无服务器、局域网发现、地址直连）都能用，但只靠同一套概念。

第 1 节是实施前的现状，保留用来说明为什么这样改。

## 1. 现状

### 1.1 身份：五种标识

| 标识 | 来源 | 问题 |
| --- | --- | --- |
| 设备密钥（Ed25519） | 本机生成，按 profile 保存 | 真正的身份，但界面上只以“指纹”出现 |
| 服务器设备 ID（16 位） | 服务器首次见到公钥时**随机**分配 | 换一台服务器就是另一个 ID |
| 本地推导 ID | 公钥哈希，仅在从未注册时使用 | 与服务器 ID 不同；首次注册后 ID 改变 |
| 协助号（9 位） | 服务器按设备分配 | 只在有服务器时存在 |
| 指纹 | 公钥哈希的另一种写法 | 用户要同时面对“设备 ID”和“指纹”两串 |

首次信任记录（`peer_keys.json`）、画质偏好等本地数据按设备 ID 存，所以 ID 一变就当成新设备。直连握手不校验对方声称的 ID 与公钥是否对应。

### 1.2 授权：六条规则

| 关系 | 谁判定 | 凭据 | 权限 | 走哪条路 |
| --- | --- | --- | --- | --- |
| 本账号设备 | 服务器（直连时用本地缓存） | 账号登录 | 全部 | 服务器、直连 |
| 好友 | 服务器 | 账号登录 | 好友授权（默认 / 按设备） | 只能经服务器 |
| 协助（经服务器） | 服务器转交 PAKE，被控校验 | 协助号 + 随机验证码 / 自定义密码 / 本机确认 | 协助模板 | 只能经服务器，主控必须登录 |
| 协助（直连） | 被控 | 地址 + 同上的验证码 / 确认 | 协助模板 | 只能直连 |
| 配对 | 被控 | 地址 + 8 位一次性配对码 | 生成配对码时选的权限 | 只能直连 |
| 已配对设备 | 被控 | 设备密钥 | 配对时的权限 | 只能直连 |

所有关系最后都与被控本机的上限（文件、端口、电源、剪贴板、人数上限）取交集，这一点是统一的。

### 1.3 秘密：七种“码”

协助随机验证码、协助自定义密码、两者均可、本机确认、8 位配对码、账号密码、服务器证书指纹。前五种都在回答同一个问题“这位陌生人能不能连我”，却分成两套设置、两套术语（“验证码 / 密码 / 配对码”），分散在三个页面（远程协助、局域网与直连、设置 → 本机被控）。

### 1.4 由此带来的问题

- 同一台设备在不同方式下 ID 不同，列表里会分散出现，偏好与信任记录跟不过去。
- “配对”和“协助”本质相同（陌生设备用一个码获得访问），只是一个会被记住、一个不会，却是两套流程。
- 已配对设备离开局域网就连不上（服务器不认识配对关系）；好友不能直连（直连不认识好友）。
- 无账号的设备不能经服务器协助别人（服务器要求账号）。
- 被控端的“谁能连我”分散在四处：设置 → 本机被控、远程协助、局域网与直连、好友。

## 2. 统一模型

三个正交的问题，各只有一个答案：

1. **你是谁** → 设备密钥，一个设备 ID。
2. **凭什么让你连** → 一张访问名单 + 一种访问码。
3. **怎么连上** → 寻址、传输、授权分开，传输自动选择。

### 2.1 身份：一把密钥，一个 ID

- **设备 ID 由公钥推导**（公钥 SHA-256 的前 80 位，base32，16 位，与现在的本地推导 ID 规则相同）。服务器不再随机分配，而是直接采用这个 ID；无服务器时也是同一个 ID。任何服务器、任何方式下，同一台设备的 ID 都相同。
- **设备 ID 就是指纹**：界面只显示一串“设备 ID”（例如 `k3x7-…`），不再另列“指纹”。直连握手与服务器注册都校验“ID = 推导(公钥)”，冒用 ID 在协议层就不可能，首次信任记录不再需要按 ID 去防冲突。
- **短号**（现在的 9 位协助号）保留，但定位为服务器分配的“拨号别名”，只用于口头告诉别人、经服务器寻址；不是身份。
- 本地按设备保存的一切（偏好、信任、配对、记住的虚拟屏）统一以设备 ID 为键。

### 2.2 授权：一张访问名单

每台被控维护一张“谁可以连接本机”名单，判定统一在被控端做，服务器只负责证明“对方属于哪个账号”和转发：

| 名单项 | 证明 | 权限 | 可经服务器 | 可直连 |
| --- | --- | --- | --- | --- |
| 本账号的设备 | 服务器签发的账号归属（直连时用缓存的本账号设备公钥） | 全部 | ✓ | ✓ |
| 好友 | 服务器签发的好友关系与授权（直连时用缓存的好友授权） | 好友授权 | ✓ | ✓（新增） |
| 受信任设备 | 设备密钥（被控本地记录） | 记录时选定 | ✓（新增） | ✓ |
| 临时访客 | 访问码或本机确认，仅本次连接 | 访客默认权限 | ✓ | ✓ |

- “已配对设备”和“记住的协助者”合并为**受信任设备**。
- 生效权限 = 名单项的权限 ∩ 本机上限（现状保留）。
- 服务器端不再为“协助”“配对”维护独立的关系类型：经服务器的会话一律交给被控按名单判定，服务器只保证寻址、限流与对方身份（设备密钥 / 账号）。这样受信任设备离开局域网也能经服务器连上，好友也能在局域网直连。

### 2.3 访问码：一种码，取代配对码与协助验证码 / 密码

| 设置 | 选项 | 对应现在的 |
| --- | --- | --- |
| 访问码类型 | 临时访问码（自动生成，可刷新，默认）/ 固定访问码（自己设定，长期有效）/ 都接受 | 随机验证码 / 自定义密码 / 两者均可 |
| 需要本机确认 | 开 / 关；只开确认、不用码也可以 | 本机确认、密码并确认 |
| 访客默认权限 | 能力编辑器（预设：仅观看 / 协作 / 完全控制） | 协助模板 |
| 连接成功后 | 被控可以“信任这台设备”（正在连接列表里的“信任”，或连接请求里的“允许并信任”），之后它无需访问码 | 8 位配对码 + 已配对设备 |

- 校验统一用现有的 SPAKE2：经服务器时由服务器转交消息，直连时在 TLS 上交换；验证码不离开两端，服务器看不到。错误次数限制与锁定沿用现有规则。
- “信任这台设备”替代配对码：不再需要单独生成一次性配对码，任何一次访客连接都可以升级为长期信任。决定权在被控一方（由被控的人点“信任”），主控不能自己申请成为受信任设备。

### 2.4 连接：寻址、传输、授权分开

- **寻址**（找到对方）：从列表点（本账号设备、好友设备、受信任设备、附近的设备），或输入 设备 ID / 短号 / 地址 之一。
- **传输**（自动选择，用户不必选）：对方在同一局域网且可达 → 直连；否则经服务器协商 P2P；再否则 TURN 中转。设置里保留“仅直连 / 仅中转”这类高级开关。
- **授权**（自动判定）：名单里有就直接连；没有就提示输入访问码，或“请求对方确认”。

主控端的界面因此只需要一个连接入口；“我的设备 / 好友 / 附近 / 受信任”是同一份设备列表的不同筛选，同一台设备只出现一次，并标出它当前可用的方式（局域网、经服务器、需要访问码）。

### 2.5 五种使用方式都只是这三层的组合

| 方式 | 身份 | 寻址 | 传输 | 可用的授权 |
| --- | --- | --- | --- | --- |
| 有服务器有账号 | 设备 ID | 列表、ID、短号、地址 | 自动 | 全部 |
| 有服务器无账号 | 设备 ID | ID、短号、地址、附近 | 自动 | 受信任设备、访问码（主控端无账号也可以，新增） |
| 无服务器 | 设备 ID | ID（附近）、地址 | 直连 | 本账号设备（缓存）、好友（缓存）、受信任设备、访问码 |
| 局域网发现 | 设备 ID | 附近列表 | 直连 | 同上 |
| 地址直连 | 设备 ID | IP / 主机名 | 直连 | 同上 |

## 3. 界面落地

- **被控端：** 一个页面“谁可以连接本机”。总开关“允许连接”、本机上限、本账号设备、好友（各人权限，跳转好友页）、受信任设备（权限、移除）、访问码（类型、刷新、需要确认、访客默认权限）。取代 设置 → 本机被控 / 远程协助的“本设备” / 局域网与直连的“配对新设备”与“可以控制本机的设备”。
- **主控端：** 一个“连接”入口：输入 设备 ID / 短号 / 地址，或从设备列表点。需要时弹出访问码输入框与“请求对方确认”。连接成功后可选“信任这台设备”。
- **术语**（全程只用这几个）：设备 ID、短号、访问码（临时 / 固定）、受信任设备、本机确认、账号密码（仅登录）、服务器证书指纹（仅服务器）。

## 4. 协议与服务端改动

| 改动 | 说明 |
| --- | --- |
| 设备注册 | 服务器以推导 ID 作为设备 ID，并校验注册请求的 ID 与公钥一致 |
| 直连握手 | `direct.hello` 校验 ID = 推导(公钥) |
| 经服务器的会话 | 新增“按设备 ID / 短号发起、由被控按名单判定”的会话目的；访问码的 PAKE 经服务器转交（复用现有协助 PAKE 通道）；主控端只需设备身份，无需账号 |
| 名单同步 | 被控向服务器只声明“是否接受访客 / 受信任设备经服务器连接”，名单本身留在本机 |
| 好友直连 | 登录时缓存好友授权（与本账号设备缓存同样签名、限时），直连握手新增 `friend` 方法 |
| 配对码 | 删除 `pair` 方法与配对码；`trust` 作为访问码连接成功后的确认步骤 |

## 5. 迁移与分阶段实施

0.1.0 尚未发布，可以一次性切换：测试服务器的设备表按推导 ID 重建（旧的随机 ID 与引用它的授权、收藏记录作废或按公钥迁移），客户端本地以设备 ID 为键的记录在首次启动时按公钥重新映射。

（2026-10-19 起这些迁移代码已全部删除，不再兼容旧版本：服务端只打开当前结构版本的数据库，其他版本拒绝启动；客户端本地记录中设备 ID 不是由其公钥推导的条目读取时直接丢弃。）

| 阶段 | 内容 | 估计 |
| --- | --- | --- |
| 1 身份 | 推导 ID 全面替代随机 ID；握手 / 注册校验；界面去掉单独的“指纹”；本地记录迁移 | 中 |
| 2 访问码 | 合并协助码 / 密码 / 配对码为访问码；“信任这台设备”；受信任设备统一存储 | 中 |
| 3 名单与经服务器访客 | 被控统一判定；受信任设备与访客可经服务器连接；无账号主控可用访问码 | 大（含服务端） |
| 4 界面 | “谁可以连接本机”一页；主控“连接”入口与统一设备列表 | 中 |
| 5 好友直连 | 缓存好友授权，直连 `friend` 方法 | 小 |

每个阶段独立可用、可测；1 和 2 不依赖服务端的大改，先做收益最大。

## 6. 取舍

- **推导 ID 暴露公钥哈希**：公钥本来就是公开的，不构成新的泄露；好处是 ID 可验证、跨服务器一致。
- **固定访问码弱于一次性码**：保留但不作默认；默认用临时访问码，长期访问推荐“信任这台设备”。服务器与被控两端的错误次数限制、锁定继续生效。
- **访问判定移到被控端**：服务器不再知道“谁是被控信任的设备”，隐私更好；代价是被控离线时无法提前判定，这与现状相同（被控离线本来也连不上）。
- **无账号主控经服务器协助**：服务器要按设备身份与 IP 限流，防止被拿来枚举短号；现有的协助限流规则可以直接沿用。

### 7.2 与提案的差异

- “好友共享”在设备页是单独的标签，不与“我的设备”混在一起（保留此前“好友的设备显示在好友名下”的要求，同时提供统一列表）；同一台设备在一个标签内只出现一次，“最近与收藏”合并本机记录与账号的经服务器记录。
- 信任由被控发起（见 2.3），没有做“主控申请信任”。
- 名单同步只用了已有的 `DevicePolicy.assist`，没有新增服务器端的名单接口：名单完全留在被控本机。
- 经服务器的受信任设备会话使用 `connect_type=assist`（游客被控也能接受），权限完全由被控本地名单决定。
- 本地按旧随机 ID 保存的画质偏好不做迁移（0.1.0 尚未发布），连接时按新 ID 重新记住。受信任设备、连接过的设备与本账号 / 好友设备缓存中，设备 ID 不是由公钥推导的记录读取时丢弃（实施时曾按公钥重新推导 ID，2026-10-19 起不再兼容）；保存 ID 与公钥不符的受信任设备报错。

### 7.4 配对与按名单自动选择方式（2026-10-21）

原先“请对方确认”并选“允许并信任”后，主控下次从“附近”连接仍走访问码 / 确认：主控只有在用设备 ID 或地址、不带访问码连接成功后，才记下“对方信任本机”。改为：

- **被控在握手时声明是否已接纳主控**：`direct.hello` 新增 `admits`（被控按本账号、好友缓存与受信任设备判定，不访问服务器）。主控每次握手都据此更新“对方是否信任本机”，并在 `admits` 为真时直接用设备密钥认证，不再弹访问码或确认。
- **请对方确认 + 允许并信任**：本次会话即以 `relation=Trusted` 接纳，下次连接自动免确认。
- **配对**（`direct.pair` / `direct.paired`）：“设备 → 附近”里对未配对的设备点“配对”。两端由同一条 TLS 连接的 EKM 推导出 6 位配对码（`crypto::pairing_code`）并各自显示；被控收到“配对请求”卡片，核对相同后点“配对”。成功后双方互相加入受信任设备，权限为完全控制，以后任一方连另一方都无需访问码或确认。配对码绑定这条 TLS 连接，中间人无法让两端显示同一个码。
- 被控同一时间只处理一个确认 / 配对请求；锁屏、界面 3 秒内未响应、或 60 秒未回答都会拒绝；主控取消或断开时请求卡片随即消失。
- “附近”列表在页面打开期间静默持续发现（间隔 2 秒，出错后 10 秒重试，8 秒内没再出现的设备才移除），不再需要手动刷新。设备旁标出“本账号 / 好友共享 / 已配对 / 对方信任本机 / 需要访问码或确认”。

这取代 7.2 中“信任由被控发起，没有做主控申请信任”：配对由主控发起，但仍须被控的人核对配对码后同意。
