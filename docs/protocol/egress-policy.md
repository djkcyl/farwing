# 服务器出口流量：上限与用户策略（设计，2026-10-30）

取代服务器设置中的“码率上限”（`bitrate_limit_mbps`，它只限制原生客户端“自定义码率”能选的最大值）。目标：管理员能限制服务器为别人转发媒体所花的出口带宽，并按用户决定能否使用中转与多人转发、能用多少。

## 0. 已确定的决定

| 事项 | 决定 |
| --- | --- |
| 用户限制 | 速率上限（Mbit/s）与每月流量配额（GB/月）都做 |
| 流量算谁的 | 主控登录的账号；访客（未登录的协助、网页 `/visit`）算被控设备主人的；转发的每条下行算该参与者的 |
| 开关 | “中转”与“多人转发”分开 |
| 出口满时 | 先把会话压低，每个会话最低 1 Mbit/s，压到底仍不够才拒绝新的中转 |
| 旧数据库 | 结构版本加一，不迁移（测试服务器重建数据库） |

## 1. 范围

- **出口流量**：服务器为会话转发媒体时发出的字节。
  - 中转（内置 TURN）：转发给客户端的、转发给对端的都算；转发到本机另一个中转地址的一跳不算（两端都经中转时那一跳在本机内）。
  - 多人转发（SFU）：发给每位观看者的下行。被控的上行是入口，不算。
  - 不算：信令、网页与接口、STUN、NAT 探测。
- **每台服务器各算各的**：控制节点和每个边缘节点各有自己的出口和上限；用户的速率上限与月配额跨所有节点合计。
- 局域网与 P2P 连接不经过服务器，不受任何限制。

## 2. 计量

- **中转**：每个分配（allocation）记两个方向的发送字节，按 TURN 用户名中的会话 ID 汇总到会话。控制节点每秒读一次本机的计数；边缘节点每秒上报一次（`FromNode::Usage`：各会话、各转发下行的累计字节与节点总量），原来 10 秒一次的健康报告不变。
- **转发**：每条下行（leg，ID 为 `会话#连接`）已有发送字节计数，按会话汇总。
- **付费方**：会话创建时确定，存在会话里。
  - 主控登录了账号：该账号。
  - 主控是访客、被控登录了账号：被控设备的主人。
  - 两边都没有账号：归入“访客”这一个公共付费方，用设置里的访客策略。
- **速率**：每秒由累计字节的差算出每个会话、每个节点、每个付费方的出口速率（取近 2 秒平均）。
- **月流量**：按付费方累计，每 60 秒（以及关机时）写入数据库 `egress_usage(payer, month, bytes)`；`month` 为服务器所在时区的 `YYYY-MM`，每月 1 日 0 点换月。

## 3. 策略

### 3.1 设置项

服务器设置新增“流量”一组（立即生效）：

| 键 | 默认 | 说明 |
| --- | --- | --- |
| `egress.limit_mbps` | 空（不限） | 本服务器的出口上限 |
| `egress.users.relay` | `true` | 账号默认可以用中转 |
| `egress.users.forward` | `true` | 账号默认可以用多人转发 |
| `egress.users.rate_mbps` | 空（不限） | 每个账号的速率上限 |
| `egress.users.quota_gb` | 空（不限） | 每个账号每月的流量 |
| `egress.guests.*` | 同上 | 访客（两边都没有账号的会话）合用的一份 |

- 每个账号可以逐项覆盖（`users` 表新增 `relay`、`forward`、`rate_mbps`、`quota_gb` 四列，空为用默认；速率与配额另可设为“不限”）。管理员账号不受限。
- 边缘节点的上限在节点设置里（原 `bandwidth_limit_mbps` 改为 `egress_limit_mbps`，含义由“超过就不再分配”改为出口上限）。
- 删除 `bitrate_limit_mbps`：服务器设置、会话票据字段与客户端的自定义码率限制一并去掉（自定义码率最高回到 500 Mbit/s）。

### 3.2 判定

对一个会话的付费方：

- **中转可用**：策略允许中转，且本月流量未用完，且至少有一个中转节点还能接纳（§4.5）。否则给出原因：`not_allowed`（策略不允许）、`quota`（本月已用完）、`busy`（出口已满或付费方的速率上限已占满）。
- **转发可用**：策略允许多人转发，且本月流量未用完。

### 3.3 会话开始

- `session.start` 时判定。中转不可用：两端拿到的 ICE 服务器只有 STUN（不发 TURN 凭据，边缘节点也不发），`SessionIncoming` 与 `SessionStarted` 带上 `relay: {allowed: false, reason}`；客户端仍按 P2P 连接。
- 服务器强制中转而中转不可用：拒绝 `session.start`，错误码 `relay_unavailable`，`details.reason` 同上。
- `SessionIncoming.forward`：这位参与者能否进转发房间。不能时被控始终让他直连，转发器也拒绝他订阅、拒绝把他的会话放进房间。

### 3.4 会话中途

- 管理员改了策略、付费方本月用完、或节点出口压到底仍超出，受影响的会话立即生效：
  - 中转不再可用：撤销该会话在各节点的分配（控制节点本机直接删除，边缘节点经 `ToNode::Revoke`），并向两端推送 `session.relays`（新的 ICE 服务器——只有 STUN——与 `relay` 状态）；客户端随即重启 ICE，能 P2P 就接上，不能就按断线结束并显示原因。
  - 转发不再可用：向被控推送 `session.relays` 中的 `forward: false`，被控让这位参与者回到直连。
- 中转恢复可用（例如管理员放开）同样推送 `session.relays`，正在走的 P2P 连接不受影响。
- 原来的 `session.relay_lost`（内置中转重启后重发中转）并入 `session.relays`。

## 4. 出口上限

### 4.1 分配

控制节点每秒为每个节点分配一次预算：

- **流**：经中转的会话（一个流，权重 1）；转发房间的主流（一个流，权重为看主流的观看者数，每位观看者的付费方各算一份）；看低码率一路的观看者按实测计入、不参与分配。
- **约束**：每个节点的出口上限；每个付费方的速率上限（跨节点）。
- **需求**：流的实测速率达到其预算的 90% 时视为还想要更多（不限）；否则为实测 × 1.5 + 1 Mbit/s（留出上升的余地）。
- **算法**：按权重的渐进填充（max-min 公平）：所有未冻结的流一起增加，某个约束用满或某个流达到需求即冻结相关的流，直到全部冻结。
- **下限**：每个流至少 1 Mbit/s（转发房间为每位观看者 1 Mbit/s）；压到下限后总量仍可能略超上限，这时不再接纳新的中转（§4.5）。
- 没有任何约束起作用时，预算为“不限”。

### 4.2 被控按预算发送

- 中转会话：控制节点经被控的实时连接推送 `session.budget {budget_kbps}`（0 为不限；变化超过 10%、或由限变为不限时才推送；`SessionIncoming.budget_kbps` 带初值）。被控把它并入这位参与者的发送上限（与转发器的上限同样处理），只在这条连接实际走中转时生效。
- 转发房间：房间的预算（每位观看者的码率）并入转发器发给被控的 REMB 上限，取两者较小；边缘节点上的房间由 `ToNode::Budgets` 下发。
- 被控按预算降码率，画质平滑变化，不靠丢包。

### 4.3 兜底限速

防止客户端不按预算发送：

- 中转：每个会话一个令牌桶（同一会话在一个节点上的所有分配共用），速率为预算的 1.3 倍（至少预算加 1 Mbit/s），突发 300 ms；每个节点一个总令牌桶，速率为上限的 1.1 倍。超出即丢包。
- 转发：每条下行同样处理。

### 4.4 显示

- 原生观看窗口的性能面板在预算起作用时显示“服务器限速 N Mbps”；网页端同样。

### 4.5 准入

- 某节点所有流都压到下限、再加一个流就超过上限时，不再为新会话提供这个节点的中转；所有中转节点都满时中转不可用（`busy`）。
- 付费方的速率上限连每个流 1 Mbit/s 都不够时，同样 `busy`。
- 转发房间在其节点满时不再开房间或加人（被控按“转发器失败”处理，30 秒后再试），参与者保持直连。

## 5. 协议改动

- 删除 `SessionTicket.bitrate_limit_mbps`。
- `SessionIncoming`：新增 `relay: RelayAccess`、`forward: bool`、`budget_kbps: u32`。`SessionStarted`：新增 `relay: RelayAccess`。`RelayAccess = {allowed: bool, reason?: "not_allowed" | "quota" | "busy"}`。
- 新消息 `session.relays`（服务器 → 两端，取代 `session.relay_lost`）：`{ice_servers, relay: RelayAccess, forward?: bool}`；`session.budget`（服务器 → 被控）：`{budget_kbps}`。
- 新错误码 `relay_unavailable`（强制中转而中转不可用）。
- 边缘节点：`FromNode::Usage`（每秒）、`ToNode::Budgets`（各会话与房间的预算、节点上限）、`ToNode::Revoke`（撤销会话的分配、退订其下行）。

## 6. 客户端

- 连接失败且中转不可用时说明原因，不再只显示“连接超时”：
  - `not_allowed`：“无法直连对方，你的账号不能使用中转”
  - `quota`：“无法直连对方，本月中转流量已用完”
  - `busy`：“无法直连对方，服务器中转繁忙”
- 观看窗口的“使用中转”在中转不可用时变灰，悬停显示同样的原因。
- 被控收到 `forward: false` 的参与者保持直连；收到 `session.budget` 后限速。

## 7. 管理端

- 服务器设置：“流量”一组（§3.1），取代“码率上限”。
- 节点页：每个节点的出口上限与当前出口速率。
- 概览：本服务器与各节点的当前出口 / 上限，本月流量最多的几个付费方。
- 用户列表：本月流量；用户详情：四项策略（默认 / 自定义）、当前速率、本月流量。
- 会话页：每个会话的出口速率与预算。
- 审计：策略变更记为 `user.policy`、`settings.update`。

## 8. 实施阶段

| 阶段 | 内容 | 验收 |
| --- | --- | --- |
| A 计量 | 数据库结构 7（用户策略列、`egress_usage`）；中转两个方向计数；会话与付费方汇总；节点每秒上报；月流量落库；概览、会话、用户页显示用量 | 强制中转观看时，概览的出口速率与观看端收到的码率相符；转发房间按观看者数计入 |
| B 策略 | 设置与用户覆盖；会话开始与中途的判定、`session.relays`、撤销分配；月配额生效；客户端提示；删除 `bitrate_limit_mbps` | 关掉某用户的中转后他的中转会话立即改走 P2P 或结束并显示原因；用完配额同样 |
| C 出口上限 | 分配器、`session.budget`、REMB 并入预算、令牌桶、准入、节点上限设置 | 上限 10 Mbit/s、两个中转会话时各约 5 Mbit/s 且画面流畅；第 11 个会话不再获得中转 |
| D 用户速率上限 | 付费方约束并入分配；访客公共付费方 | 某用户上限 4 Mbit/s 时他的两个会话合计不超过 4 Mbit/s，别人不受影响 |

## 9. 实施状态

### 阶段 A（2026-10-30，已完成）

- 中转：每个分配经会话的计量器发送（`vendor/turn` 的 `Egress` / `Gauge`），两个方向都计；转发到本中转端口范围内另一个分配的一跳不计。转发：每条下行写出前计入该会话。每包另计 36 字节（IP、UDP 与 TURN / SRTP 封装）。
- 控制节点每秒汇总本机，边缘节点每秒上报 `FromNode::Usage`；健康报告的 `relayed_bps` 改为 `egress_bps`（中转与转发合计）。
- 付费方在会话创建时确定；月流量每分钟与关机时写入 `egress_usage`（UTC 自然月，网页按本地时间显示重置时间）。数据库结构版本 7（另含 §3.1 的用户策略列）。
- 管理端：概览“出口”与“本月流量”（前 5 位），会话页“出口”列，用户列表“本月流量”列，用户详情“本月流量”。
- 验收：本机临时服务端，强制中转时会话 578–614 kbps，与观看端收到的码率（约 0.56 Mbps 视频加声音）相符；阈值 2 的转发房间两位观看者各约 1.1 Mbps，分别计入两个账号；月流量按分钟落库。
