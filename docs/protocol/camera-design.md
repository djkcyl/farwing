# 远程摄像头、媒体模块复用与端到端加密开关（设计，2026-11-01）

三件事，在聊天（[chat-design.md](chat-design.md)）之前做：

1. **远程摄像头**作为主功能：在设备中心与网页上查看被控设备的摄像头，可调采集参数（像 OBS 的视频采集设备：默认与自定义）。
2. **媒体模块复用改造**：把被控的采集—编码—发送链路、观看端的解码—呈现链路从“远程桌面的屏幕”里解开，摄像头先用上，聊天的摄像头与屏幕共享随后复用。
3. **端到端加密总开关**：服务器设置三档，客户端也可强制只接受端到端，多人转发与以后的聊天都按它走。

## 0. 已确定的决定

| 事项 | 决定 |
| --- | --- |
| 权限 | 新增能力 `camera`（看摄像头）与 `listen`（听被控的麦克风）；好友授权里各一项，默认不授予；访客模板没有；本账号设备有 |
| 被控开关 | “允许远程查看摄像头”“允许远程收听麦克风”两个开关，默认都关；收听用哪个麦克风由主人选 |
| 被控提示 | 被查看期间屏幕角落显示“摄像头正在被某某查看”与停止按钮（不进入画面），开始时发一条通知 |
| 入口 | 设备卡片与详情的“摄像头”直接打开只看摄像头的窗口；看屏幕时可在工具栏切到摄像头或开画中画；网页功能相同 |
| 参数 | 被控主人为每个摄像头设默认（默认或自定义）；观看者可临时自定义（按设备记住）；多人同时看时以最先开始看的人的参数为准 |
| 自定义项 | 分辨率与帧率、视频格式与色彩、画面调整、镜像与旋转、码率上限（只显示设备支持的） |
| 多摄像头 | 一次看一个，可切换 |
| 占用 | 尽量共享打开；被其他程序独占时提示“摄像头正被其他程序使用”，不抢占 |
| 传输 | 摄像头与屏幕同等：同参数的观看者共用编码，人数达到多人转发阈值时走转发 |
| 码率 | 分辨率与帧率按参数，码率按网络自适应，上限按分辨率取默认值，自定义可改 |
| 端到端总开关 | 服务器设置“端到端加密”：强制 / 允许兼容（默认）/ 关闭；客户端设置“只接受端到端加密” |

## 1. 范围

- **做**：§0 所列；被控为本机 Windows（原生客户端），观看端为原生与网页。
- **不做**：同时看多个摄像头、摄像头录像、云台控制（PTZ 中只做变焦）、虚拟摄像头输出、手机摄像头。
- 聊天里的摄像头（[chat-design.md](chat-design.md) §8.1）用本文的采集与参数，发送走聊天的转发器。

## 2. 权限与开关

- **能力**：`camera`（看摄像头，含切换与调参数）、`listen`（收听被控的麦克风）。
  - 加入 `caps::ALL`；网页端可用的能力（服务器设置“网页端可以使用的功能”）默认包含两者。
  - 本账号设备拥有全部能力；好友授权默认不含；访客模板不含（访客访问码确认弹窗里也不提供）。
- **被控开关**（被控设置“摄像头与麦克风”一组）：
  - “允许远程查看摄像头”，默认关；
  - “允许远程收听麦克风”，默认关，下面选麦克风（默认跟随系统默认录音设备）。
  - 两者发布到服务器的设备策略：`DevicePolicy.camera`、`DevicePolicy.listen`。
- **判断**：会话或请求同时满足“对方有能力”与“被控开着开关”才允许。
  - 服务端：`Purpose::Camera` 的会话需要 `camera` 能力与 `policy.camera`，否则 `403`。
  - 被控：再按本机设置核对一遍，不满足时拒绝 `CameraControl` / `ListenControl`。

## 3. 摄像头采集（被控）

### 3.1 枚举与打开

- 用 Media Foundation：`MFEnumDeviceSources`（视频采集类）枚举，按设备的符号链接识别（重新插拔仍是同一个）。
- 每个摄像头读出支持的媒体类型：分辨率、帧率、像素格式（NV12、YUY2、MJPEG、H.264 等）。
  - 同一分辨率与帧率有多种格式时，默认优先 NV12 → YUY2 → MJPEG；H.264 只在自定义里可选。
- 打开时优先共享模式（Windows 帧服务器允许多个程序同时用同一摄像头）。
  - 共享打开时，如果其他程序已在用，只能用它正在用的格式：这时界面显示“参数由正在使用摄像头的程序决定”，自定义的分辨率与格式不可选。
  - 共享失败而独占也失败时，报告“摄像头正被其他程序使用”。
  - Windows 隐私设置不允许桌面程序使用摄像头时，报告对应原因（并说明在“设置 → 隐私和安全性 → 摄像头”里打开）。

### 3.2 帧处理

- **读帧**：Source Reader 读帧，MJPEG 由 Media Foundation 解成 NV12（有显卡解码时走 `IMFDXGIDeviceManager` 直接得到 D3D11 纹理）。
- **转换**：NV12 / YUY2 转为 BGRA 纹理（复用观看端 `video_shader` 的 YUV 着色器）。
  - 色彩空间（BT.601 / BT.709）与范围（有限 / 完整）默认按设备报告，自定义可强制。
- **镜像与旋转**：在同一次着色中完成，然后进入现有的缩放与编码（`preprocess`）。
- **统一出口**：输出与桌面采集相同的帧（`capture::Frame`），经 §9.1 的 `FrameSource` 进入编码组。
- **画面调整**：亮度、对比度、饱和度、锐度、伽马、白平衡、曝光、对焦、变焦、防闪烁（50/60 Hz）。
  - 实现：经媒体源的 `IAMVideoProcAmp` 与 `IAMCameraControl` 读写（范围、步长、默认值、是否支持自动），实时生效，不重启采集。
  - 设备不支持的项不显示。

### 3.3 在哪个进程采集

- **便携被控**：在被控进程里采集。
- **装了后台服务**：在当前登录用户会话中的用户进程里采集（与剪贴板、文件等相同的普通用户执行端），帧经共享纹理交给被控，方式同桌面采集代理。
  - 没有用户登录时不能查看摄像头（提示“当前没有用户登录”）。
- 摄像头不绑定某块显卡，编码器所在显卡自由选择（优先与解码 MJPEG 的同一块）。

### 3.4 默认参数

- “默认”为：1080p30 → 720p30 → 设备的最高分辨率（帧率 ≤ 30），格式按 §3.1 的优先级，色彩按设备报告，不镜像、不旋转，码率上限按 §7。
- 被控主人可为每个摄像头保存“自定义”，作为这台设备该摄像头的默认。

## 4. 协议

### 4.1 会话目的与能力

- `Purpose::Camera`：只看摄像头的会话（`required_cap = camera`）。
  - 被控为它建一个没有显示器、键鼠、剪贴板与文件功能的参与者，只发摄像头画面（与 `listen` 打开时的麦克风声音）。
- `Purpose::Desktop` 的会话：对方有 `camera` 能力时，也可以在会话中打开摄像头（切换或画中画）。
- 对端 HELLO 新增特性 `camera`；对方不支持时，观看端不显示摄像头入口。

### 4.2 SESSION 消息（新增，[peer-messages.md](peer-messages.md) 同步更新）

| 消息 | 方向 | 内容 |
| --- | --- | --- |
| `Cameras` | 被控 → 观看端 | 摄像头列表：`id`、名称、是否可用（及原因）、支持的媒体类型、画面调整项（范围、步长、默认、当前、是否自动）、主人的默认参数、当前是否共享打开 |
| `CameraControl` | 观看端 → 被控 | `{camera, start, track, params?}`：在某条视频轨上开始或停止某个摄像头；`params` 为空用默认 |
| `CameraParams` | 观看端 → 被控 | 修改正在看的摄像头的参数（重开采集；画面调整不走这里） |
| `CameraAdjust` | 观看端 → 被控 | `{camera, control, value, auto}`：实时画面调整 |
| `CameraState` | 被控 → 观看端 | 每条摄像头轨的实际参数、由谁决定（“正在使用某某的设置”或“由其他程序决定”）、错误 |
| `ListenControl` | 观看端 → 被控 | `{start}`：开始或停止收听麦克风（声音走新增的 `audio_1` 轨） |

- `TrackState` 加 `source`（`screen` 或 `camera`）与 `camera`（摄像头 ID），观看端据此标注与布局。
- 轨道池：视频轨仍为 `video_0…`；摄像头占用其中一条空闲轨。音频轨池增加 `audio_1`（被控的麦克风），SDP 两端同步增加。

### 4.3 多人观看与转发

- 同一摄像头的编码组键 = 摄像头 ID + 实际参数 + 输出格式。
  - 后来的观看者加入已有的组，界面显示“正在使用某某的设置”。他们的自定义只在成为第一个观看者时（前面的人都离开后）生效。
- 摄像头的编码组与屏幕的一样，可以作为上行（多人转发）的观察者成员：达到阈值时，摄像头轨经转发器发出。
  - `Forward.tracks` 照常映射；网页观看端可以同时接收屏幕与摄像头两路（画中画）。

## 5. 被控端界面与行为

- **被控设置“摄像头与麦克风”**：两个开关、麦克风选择，以及摄像头列表。每个摄像头可点“设置”，打开与观看端相同的参数面板（默认 / 自定义），作为默认保存。
- **角落提示**：有人在看摄像头或收听麦克风时，在主屏右下角显示一个小窗：“摄像头正在被 爱丽丝 查看”（收听麦克风时写“摄像头与麦克风”），带“停止”按钮。
  - 这个小窗排除在屏幕采集之外（`WDA_EXCLUDEFROMCAPTURE`），远程看屏幕的人看不到它。
  - 点“停止”结束这些摄像头与收听，并在本次会话中不再允许重新打开。
- **通知**：开始被查看时发一条通知（新的通知种类“摄像头或麦克风被查看”，默认开，见 [notifications.md](../notifications.md)），记录写入连接记录。

## 6. 观看端界面

### 6.1 原生

- **入口**：设备卡片与详情页的“摄像头”按钮：对方在线、有 `camera` 能力且被控开着开关时可用，否则灰色并说明原因。点开为只看摄像头的观看窗口。
- **只看摄像头的窗口**：复用观看窗口（§9.4 的 `VideoPlayback` 加“摄像头模式”），没有键鼠、剪贴板、文件、批注与显示器菜单。
  - 工具栏：摄像头选择、参数、收听麦克风、截图、全屏、性能监控。
- **看屏幕的窗口**：工具栏新增“摄像头”菜单：切到摄像头（主画面换成摄像头）、画中画（摄像头小窗叠在屏幕画面一角，可拖动、可缩放、可隐藏），以及参数入口。
- **参数面板**（像 OBS 的视频采集设备属性）：
  - 设备；“默认 / 自定义”；
  - 自定义下：分辨率与帧率（下拉，来自设备列表）、视频格式、色彩空间与范围、镜像、旋转、码率上限；
  - 画面调整：每项一个滑杆加“自动”勾选，实时生效，可“恢复默认”。
  - 观看者的自定义按设备记住；“恢复为主人的默认”一键回到被控主人的默认。

### 6.2 网页

功能与原生一致：设备列表与观看页有“摄像头”入口，可切换、画中画（第二个 `<video>`）、调参数、收听麦克风，受服务器“网页端可以使用的功能”限制。

## 7. 画质与码率

- 采集分辨率与帧率按参数，编码分辨率与之相同（不按屏幕的画质档缩放）。
- 码率走现有拥塞控制，上限默认：

  | 分辨率 | 30 帧 | 60 帧 |
  | --- | --- | --- |
  | ≤ 480p | 1.5 Mbps | 2.5 Mbps |
  | 720p | 3 Mbps | 4.5 Mbps |
  | 1080p | 5 Mbps | 8 Mbps |
  | 1440p 及以上 | 8 Mbps | 12 Mbps |

  自定义里可改为 0.3–20 Mbps。
- 弱网时先降码率再降帧率（不低于 15 帧），不自动降分辨率。
- 观看窗口的“画质”菜单对摄像头只显示帧率上限与弱网策略。

## 8. 端到端加密总开关（项目范围）

### 8.1 服务器设置

服务器设置“端到端加密”取代多人转发里的“允许兼容模式”（`sfu.allow_compatible`）：

| 档位 | 含义 |
| --- | --- |
| 强制 | 经服务器转发的媒体只能端到端加密；兼容模式不可选 |
| 允许兼容（默认） | 默认端到端；各功能的主人可选兼容模式：多人转发由被控主人选（被控设置“多人转发”），聊天的语音频道由群主按频道选 |
| 关闭 | 所有经服务器转发的媒体都用兼容模式（服务器能读到媒体，为以后的录制、转码等留门） |

- `ServerInfo.features` 新增 `e2ee: "required" | "allowed" | "off"`；`forwarding.modes` 随之给出（强制：只有 `e2ee`；关闭：只有 `compatible`）。
- 服务端在 `POST /sfu/rooms`（以及以后的聊天语音）按档位校验模式。

### 8.2 客户端“只接受端到端加密”

客户端设置（默认关）：

- **作为被控**：只用端到端加密的多人转发。服务器为“关闭”时不走转发，观看者全部直连。
- **作为观看者**：在 `ConnectOptions` 中声明 `e2ee_only`。
  - 被控的转发房间是兼容模式时，不把这位观看者放进房间（保持直连）。
  - 聊天里不进入兼容模式的语音频道（提示原因）。
- 点对点与经中转的会话本来就是两端之间的 DTLS-SRTP 加密，不受影响。

## 9. 媒体模块复用改造

依据对现有代码的梳理（被控 `features/host`、`media`、`platform/windows`，观看端 `application/viewer`，服务端 `sfu`），分四步。每步行为不变，回归后提交。

### 9.1 采集源接口（`FrameSource`）

**现状**：

- 编码链路 `pipeline::run` 写死了 `capture::Desktop`：`Desktop::open_selected(&screen)`、读 `cursor`、`generation`、`available`、`hdr_available()`、`device`。
- 编码组键 `encode_group::Key.screen`、`Key.cursor` 与输出 `Output.screen: capture::Screen` 都以显示器为单位。
- 编码能力探测 `encoder::probe(&mut Desktop)` 要用真实的桌面帧，能力缓存也按屏幕。

**改造**：

- 引入 `trait FrameSource`：`device()`、`generation()`、`available()`、`hdr_available()`、`backend_name()`、`cursor()`（默认无）、`next(wait, request) -> capture::Frame`。由 `capture::Desktop` 实现，以后加摄像头源与窗口采集源。
- `pipeline::Start` 改为 `SourceSpec { Screen(Screen) | Camera(CameraSpec) }`，带 `open()`。
- `Key.screen` 改为 `SourceKey`；`Output.screen` 改为 `SourceDescriptor`（尺寸、帧率、显卡、名称、种类）。
- 光标只对屏幕源有意义。
- `encoder::probe` 改为接受任意 `FrameSource` 或合成的测试纹理；能力缓存键改为源描述。

### 9.2 与源无关的轨道与状态

**现状**：

- 轨道槽 `Slot.screen: Option<capture::Screen>`，以及 `Lease::source/encoder`、`StreamStatus.screen`、`TrackState.screen`，都写死为屏幕。
- 被控的 `Peer` 把媒体连接与桌面功能（显示器拓扑、键鼠坐标、剪贴板、光标、共享观看流）绑在一起。

**改造**：

- `Slot.source: Option<Source>`，`Published.source`、`StreamStatus.source`、`Lease::encoder` 与采集线程都用源描述；只与屏幕有关的逻辑（显示器拓扑、无头屏、恢复）经 `Slot::screen()` 只看屏幕源。`show_at` 在任一轨上显示任一种源。
- 只看摄像头的参与者沿用现有“只听声音”参与者的做法：同一个 `Peer`，不准备显示器，不开键鼠、剪贴板、文件与批注（§4.1），而不是另拆一层。
- 媒体引擎的编解码注册统一到 `farwing_rtc_wire::register_codecs_where`（被控只注册能编码的格式）。

### 9.3 可复用的发送轨

把“视频轨 + 传输分叉 + 发送 / 反馈 / 报告任务 + 编码组成员”打包成一个构件。现在上行（`uplink.rs`）是手工拼出来的。

- 摄像头、聊天的 `cam_hi`、`cam_lo`、`screen`、`screen_720` 都是它的实例。
- 每条轨可挂帧加密（按发送者的密钥）。
- 长期参考恢复的反馈来源可插拔（现在只从远程桌面的控制通道来）。

### 9.4 观看端的 `VideoPlayback` 与观看模式

**现状**：解码（`decode_pipeline`）、呈现队列与渲染线程本身可复用，但观看会话 `NativeViewerSession` 与窗口 `ThreadedWindowsApp` 绑定了 `StreamControlHandle`。它是键鼠、拖放、批注、显示器菜单、剪贴板等一切功能的入口。

**改造**：

- 抽出 `VideoPlayback`：解码线程、呈现队列、渲染线程、视频窗口。只需要一个帧来源、一个反馈出口与一个画面比例来源，任何 `VideoFrameSink`（点对点、转发、以后的聊天转发器）都能喂。
- 观看窗口加“观看模式”（桌面 / 摄像头 / 以后的聊天直播），按模式启用键鼠、钩子、拖放、批注与显示器菜单。
- 渲染支持镜像与旋转（着色器参数）。

### 9.5 声音的构件（步 A1，聊天语音之前）

- 把被控虚拟麦克风里已有的多路 NetEq 混音（`features/host/microphone.rs`）泛化为 `AudioMixer<Sink>`；
- 把 `media::microphone` 的采集与“远程麦克风”的状态机分开；
- 按 NetEq 的方式编入 WebRTC 音频处理模块；
- 增加按进程回环采集；
- 注册 `ssrc-audio-level`（注意扩展 ID 的共享注册顺序）。

多发布者的转发器房间与按发送者的解密器在聊天的语音阶段做（[chat-design.md](chat-design.md) §14.2）。
