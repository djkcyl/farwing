# Farwing 0.1.0 单机自测结果

日期：2026-10-15（第二轮自测在同日 UAC 更新之后，覆盖后台服务模式与设备中心界面）。一台机器（Windows 11 26200，RTX 5060 Laptop + Intel 核显，2560×1600 @150%，另有 Clash TUN 网卡 198.18.0.1）上，以多个 profile 分别充当被控与主控，服务端为本机 `https://localhost:18443`（`temp/e2e2`）。被控 H 为 `--profile b host`（便携模式，未走后台服务），主控为 alice（`a` 及 `g`、`h`、`l`、`m` 等同账号 profile）、bob（`c`，alice 的好友）与 carol（`p`）。项目编号对应 [manual-test-checklist.md](manual-test-checklist.md)。

“PASS”只说明单机回环上的行为符合预期；双机、真实局域网和公网上的表现仍以清单为准。

## 1. 本轮发现并已修复的问题

| 问题 | 原因与修复 |
| --- | --- |
| 协助会话在被控重启后放弃恢复（`not_found`） | 协助会话的服务端会话随被控下线而结束，旧会话无法刷新票据。现在保留本次会话的验证码，刷新返回 `not_found` 时用同一验证码向同一设备重新授权；被控离线期间按退避重试（`recovery_for`）。 |
| 观影模式（包括多人观看流）总是出现高延迟告警 | 约 120 ms 的观影缓冲被计入“估算帧延迟”和“本地单帧”，超过 60 / 100 ms 的阈值。现在记录每帧在缓冲中的等待时间，判断告警时扣除，显示值不变；超出缓冲的延迟照常告警。修正后观看者 frm. 约 121 ms、为绿色，没有告警图标 |
| 等待恢复页面没有保留最后一帧 | 快照取自已不再使用的旧 `playing` 槽位，总是退回设备壁纸。现在从多屏窗口的渲染器截取。 |
| 被控端端口转发目标为主机名时不通 | 只连接解析出的第一个地址（`localhost` → `::1`，而服务只监听 IPv4）。TCP 现在按 happy eyeballs 依次尝试全部地址。`dev ports --remote` 同时支持 `主机名:端口`。 |
| 好友获得“文件传输 / 端口转发 / 诊断包”授权后仍无法使用 | 三个服务与设备详情页只接受本账号设备。新增 `DeviceList::with_capability`（本账号设备，或已授予该能力的好友设备），三个服务与设备详情页的按钮按授权显示。 |
| 无法添加虚拟屏（`目标显示器未启用` / `虚拟显示器创建后未出现`） | Windows 会先把新的间接显示器通过渲染 GPU 以克隆主屏的方式接入，路径的适配器与目标 ID 与驱动返回的不同，原代码按驱动返回的 ID 匹配。现在按显示器身份匹配；布局应用在新显示器尚不可用时重试；等待新路径激活后再设 DPI；常驻兜底屏同样按身份识别；`FWG0001` EDID 标记为 Farwing 显示器。 |
| 观看窗口用“显示设置”页切换超级屏 / 删除虚拟屏后，画质菜单再也打不开 | `topology_menu::entries` 在 `egui::Window` 内调用 `ui.close()`，窗口此后一直被压成 2×2 像素。现在由调用方自行关闭（画质菜单改状态，标签右键菜单仍用 `ui.close()`）。 |
| 服务器不可用时启动的被控不接受直连 | CLI 被控在 `list_devices` 上等待服务器；“允许被控”的开启在 `publish_policy` 上等待服务器，直连会话因此拿不到授权。现在 CLI 继续启动（“服务器暂不可用，先只接受直连”），开启被控时的策略发布限时 10 s，超时后进入“服务器暂不可用，仅接受直连”。 |
| 单元测试 `blocking_control_masks_the_capability_for_one_participant` 在已安装后台服务的机器上失败 | 测试经由 `resident::managed()` 走了后台服务分支。测试改为直接调用便携路径。 |
| 多人会话中先加入的若是只能观看的好友，后加入的本账号参与者也不能添加虚拟屏（8.7） | 多位参与者共用的显示会话以“主机级租约 + 第一位参与者的授权”创建，`Session::create` 用这份租约检查 `display`。按你的决定改为检查发起者自己的租约（检查保留，只换成调用者的授权）。 |
| 被对方结束的会话（踢出、删除配对、撤销授权）窗口仍然直接消失 | 显示“连接已结束”时发出的重连事件没人确认，窗口把它当成失败退出。现在由会话侧确认，窗口停在“连接已结束 · 原因 · 关闭窗口”。 |
| 游客模式一直停在“正在启用被控…”；后台服务启动时被控开启要卡 10 s | `SignalSession::run_host` 处理被控事件时不再轮询正在申请在线票据的 future；该请求持有账号 / 游客 API 的锁，事件里的 `publish_policy` 又要这把锁，形成死锁（上午加的 10 s 超时把它变成 10 s 卡顿外加一条过期的“服务器暂不可用，仅接受直连”）。现在处理事件时继续轮询；策略发布成功后清掉“仅接受直连”提示。 |
| 冷启动的编码器探测超过主控 12 s 连接期限，并且每次重试都从头探测 | 探测随触发它的参与者取消，结果永远进不了缓存（游客被控、充当本设备被控的 CLI 观看进程、新版本首次启动都会遇到）。现在探测按被控生命周期运行，参与者放弃后继续完成，重试即可连上；游客被控在启动时就预先探测（与已登录设备中心一致）。 |
| 被控关闭“端口转发”后，主控本地的转发连接不会断开，只是卡住 | 被控在权限变化时只在本地复位转发流，主控收不到复位。现在先向主控发送每条流的复位（“被控端已关闭端口转发”）。 |
| 卸载程序时若还有其他 profile 的窗口运行安装目录中的 `Farwing.exe`，先卸掉驱动和服务，最后删程序文件才失败（“程序操作失败，请查看日志（退出码 1）”），留下半卸载状态 | 卸载只关闭当前 profile 的设备中心，文件占用到最后一步才发现。现在在动任何组件之前检查运行安装映像的用户进程，有则直接失败并提示“仍有 Farwing 程序在运行（可能是以 --profile 启动的其他实例或观看窗口），请全部关闭后重试”（退出码 32）。已在实机验证：开着一个 `--profile` 窗口时卸载会立即停止并提示，驱动、服务、程序都不受影响。 |
| 人数上限的拒绝提示是旧的“目标已有其他主控” | 服务端 `busy` 的文字沿用了单主控时代的说法，规范中 `busy` 表示“被控参与者已满”。改为“被控端同时连接人数已达上限”。 |
| 编码器达到上限时，“最接近的组”只看画面大小，不看帧率 | 尺寸相同的组之间再按帧率接近程度选择（新增单元测试）。 |

此前（同日）已修复并记录在案的：后台服务保管库只用于默认 profile；后台服务读取不到服务器设置（服务器设置随账号进入保管库）；被撤销 / 被移除好友时观看窗口直接消失（改为显示“连接已结束”及原因）；SDK 与 WDK 版本分离的驱动构建脚本；`verify.ps1` 对未受信任自签名根证书的校验。

## 16. 播放流畅性（2026-10-18）

用 `dev video --fps 60` 量解码端的帧间隔、冻结与抖动：被控为本机 NVENC（只支持 API 13 之后的构建），1728×1080 @ 60 fps，画面是持续变化的测试动画，每项 30 秒，视频包统一加 20 ms 延迟（“60 ms”一行加 60 ms）。注入的丢包发生在重传与 FEC 之后，修不回来，是最坏情况；实际使用中多数丢包会先被重传修好，不走这条路径。本机回环不限带宽，所以关键帧的传输时间没有体现，真实链路上只用关键帧的结果会比表中更差。

结论：

- 没有丢包时，这些改动不改变播放节奏：长期参考开 / 关的帧间隔、抖动、帧大小都相同，所有测试中都没有丢包以外的停顿。
- 每次修不回来的丢包仍会让画面停一下，约为“1.5 倍 RTT 的等待 + 一次往返 + 一帧”：20 ms 延迟时约 100 ms，60 ms 延迟时约 190 ms。这是“宁可停也不显示错误画面”的设计结果；等待那 1.5 倍 RTT 是为了先给重传机会。
- 只用关键帧时，随机丢包下关键帧本身（约 270 KB、数百个包）容易再次被丢，形成 0.5–1.1 秒的连续冻结；恢复帧（p50 5–18 KB）基本不会。随机丢包下冻结合计从 7.9 秒降到 2.0 秒，数据量少 74%。
- 仍会出现较长冻结的情况：恢复没有在兜底时间内完成（例如恢复帧本身也被丢）时退回关键帧，60 ms 一行的 3 次 ≥250 ms 冻结中 2 次是这样；距上次确认的参考画面变化很大时，恢复帧会接近半个关键帧大小（该行最大约 120 KB）。

## 19. 不倒退检查、追帧与链路模拟（2026-10-18）

要求：任何场景、任何一端都不能比改动前差。做法：把上一轮结束时的程序冻结为基线（`temp/baseline`，哈希 `4f17a93e`），与新程序在同一台被控上交替运行同一组场景，每项重复多次，比较平均值、范围与中位数（脚本 `temp/reg/native.sh`、`window.sh`、`compare.py`）。场景：无窗口解码（无丢包 H.264 / H.265 / AV1、约 6 % 可修复丢包、每 3 秒丢一整帧、20 Mbps 瓶颈）与真实播放窗口（无丢包、可修复丢包、整帧丢失）。

**浏览器 PLI 改用恢复帧（未采用）**：对确认过参考的 Chrome，用恢复帧回应它自己发的 PLI；在被控链路模拟约 6 % 丢包下出现 3 次，每次 Chrome 都在约 200 ms 后再次发 PLI、最后靠关键帧恢复（它发出 PLI 后只接受关键帧），只会多等 200 ms，已撤回。

**默认行为的结论**：恢复帧、恢复帧重试、提前判定、浏览器的描述符恢复与“拒绝重传时立即出关键帧”、设备上线推送、光标颜色立即生效、新参与者先跟随编码组、追帧（低延迟播放、高刷新率屏幕）都作为默认行为，不提供界面开关（恢复帧保留 `FARWING_NVENC_LTR=0` 作排障用）；浏览器的描述符只在验证过的 Chromium 内核浏览器（Chrome、Edge）中请求，其他浏览器保持原来的行为（用 Chrome 模拟没有 `userAgentData` 的浏览器时 offer 不带描述符、播放正常）；AMD / Intel 的长期参考在对应显卡上验证前继续默认关闭；各测量开关只用环境变量或隐藏参数。

**链路模拟（`FARWING_HOST_LINK`）**：第一版只延迟视频，声音不经过模拟链路，而两者共用传输层序号，声音“超车”让被控以为丢了 20–30 % 的包、码率降到下限；改为声音同走一条链路后，只设 `delay:25` 时被控报告丢包 0、RTT 43–46 ms、码率正常。`net:0.01,0.3;rate:12;delay:25` 下被控的拥塞控制把码率稳定在 7–8 Mbps，重传修好绝大多数丢包，30 秒内 1–2 次 ≥100 ms 停顿；此时恢复帧与只用关键帧接近（关键帧 1 对 3–4、最长间隔 156–171 对 181–187 ms）。

**浏览器在真实丢包下**（`FARWING_HOST_LINK="net:0.02,0.3;delay:30"`，约 6 % 可修复丢包，Chrome H.264，每次 30 秒）：协商描述符 2 次与不协商 3 次的停顿数（11–13）、冻结合计（1.7–2.0 s）相当，两种情况各出现一次约 350 ms 的停顿并伴随 Chrome 自己的 PLI（重传反复丢失后它放弃该包），描述符没有带来倒退；它的收益在被控无法重传时（§18：约 3 s 冻结变为 48 ms）。为此把“告诉浏览器不再等待”的空包限定为该包已不在重传历史中，速率或预算造成的暂时拒绝不再发送，让浏览器之后的重传请求仍有机会。

**关键帧之后的恢复帧偏大**：只在关键帧后约 0.5 秒内出现丢包时发生（参考只能是关键帧附近的帧，80–150 KB）；此时的替代方案是约 230 KB 的关键帧，恢复帧仍然更小，压缩其大小会降低画质，所以不改。

## 20. 弱网 FEC（2026-10-19）

**问题**：RS-FEC（[farwing-protocol.md](protocol/farwing-protocol.md) §6.4）从未真正发出。内置 WebRTC 库的发送、接收与 SDP 代码仍按旧名称 `video/rs-fec-cm256` 识别 FEC 流，而 Farwing 的编解码名称是 `video/x-farwing-rsfec`，两端都没有建立 FEC 流（被控调试日志 `no FEC stream bound`），弱网下只靠重传。改为库导出的同一个常量后，FEC 流建立。

**最终策略**（为了任何场景都不倒退）：

- 测得丢包率低于 0.5 % 时不发 FEC，也不为修复包头预留包长：网络正常时发出的包与原来完全相同。
- FEC 只用富余带宽：媒体与重传低于带宽估计的 60 % 时，修复包补到 60 % 为止；编码器码率不因 FEC 扣减。带宽被画面用满时不发，行为与原来相同。
- `FARWING_FEC=0` 关闭；浏览器不协商这个编解码，不受影响。

**为什么这样限制**（试过的三个版本，测量方法同 §19：被控端链路模拟，同一程序 `FARWING_FEC=1 / 0` 交替运行）：

1. 按原设计把 FEC 占用从编码器码率中扣除：约 2 % 随机丢包下改善明显（接收间隔 p95 61 → 31 ms、延迟 p95 46 → 34 ms、小卡顿 3.5 → 2），但 6 Mbps 瓶颈加丢包时编码器码率被压到档位的 1/4 以下，被控随之降帧（渲染帧率 54 → 44 fps）。
2. FEC 只用媒体剩下的带宽（补到估计的 90 %）：瓶颈场景恢复（58.5 / 59.0 fps），但发送量接近估计后，拥塞控制不再认为发送端“没用满带宽”，也就不再探测。丢包下码率只能靠探测上涨：首次连接的重度丢包与随机丢包两个场景合计，关 FEC 时 10 次中有 5 次涨到 3 Mbps 以上（最高 16 Mbps），开 FEC 时 10 次中只有 1 次，帧率因此更低。
3. 最终版：总发送量不超过估计的 60 %（拥塞控制在 85 % 以下才算没用满），探测照常进行；同样统计，开 / 关 10 次中分别有 4 / 5 次涨上去。

**最终版本的结果**（画面持续运动，每组 5 对，中位数，开 / 关）：

|---|---|---|---|---|---|---|
| 随机丢包约 2 %，单程 30 ms | 60.2 / 59.9 | 0 / 2 | 39.7 / 47.4、71.5 / 79.5 ms | 5 / 7 | 1664 / 2400 | 208 / 0 |
| 重度丢包约 6 %、成串，单程 40 ms | 55.9 / 50.9 | 6 / 6 | 63.9 / 63.9、94.1 / 83.5 ms | 27 / 40 | 2478 / 3365 | 465 / 0 |

**与基线的完整回归**（基线程序与本轮程序交替，被控与主控都换，画面持续运动，每次清掉记住的码率，各 3 次，中位数）：无窗口解码的无丢包 H.264 / H.265 / AV1、20 Mbps 瓶颈、整帧丢失，以及播放窗口的无丢包、整帧丢失：帧数、帧间隔、延迟持平（收到的数据量更高，与帧数无关）。播放窗口的可修复丢包：未显示的帧 108 → 21、渲染帧率 55.9 → 57.4、延迟 p95 64.5 / 64.4 ms、最长渲染间隔 130 / 129 ms。无窗口解码的可修复丢包（丢包注入在主控收包处，被控看不到，不会发 FEC）：解出的帧 1637 → 1767（范围分开），≥100 ms 间隔 13 → 18、冻结 1.5 → 2.0 s（范围重叠）；§19 也是同一方向。为确认与本轮无关，同一程序对比主控建立 / 不建立修复流（主控 `FARWING_FEC=0`）各 5 次：≥100 ms 间隔 16 / 16、冻结 1.73 / 1.80 s、解出帧数相同，修复流本身没有影响。

**测量方法的教训**：被控会记住上次会话收敛的码率作为下次起点，画面内容（终端文字还是运动画面）决定帧的大小，两者都会让交替运行的两组起点不同；最终的对比每次都清掉或固定这个起点，并用 `temp/enc/anim.py` 保持画面运动。

## 21. 丢包网络的首次连接与码率探测（2026-10-19）

**问题**：随机丢包（2–10 %）的网络上，首次连接（被控没有记住上次的码率）约一半整场停在 1.5–2.5 Mbps，画面持续运动时帧率掉到 30–45 fps。丢包率在 2–10 % 之间时，基于丢包的码率估计既不升也不降，只有探测成功才能往上涨；而探测几乎从不成功。

**根因**：被控的探测发送循环按 2 ms 一步排期，但运行时定时器在默认的 Windows 时钟精度下常常晚醒 5–15 ms，原代码落后 10 ms 就放弃整个探测簇。码率低时每步只发一个包，于是每个探测簇只发出 1–2 个包，接收端凑不够 4 个，探测没有结果（调试日志：每 5 秒一次 `WaitingForProbingResult: timeout`）。开播时的初始探测和带宽有空余时的周期探测同样受影响，所以首次连接能不能涨起来像抽签；浏览器观看者也一样。

**修复**：探测簇发送期间改用高精度可等待定时器（与鼠标发送定时器相同）按 2 ms 节拍发送；晚醒时最多补发两步，落后 30 ms 才放弃；簇的完成条件按已发的包数（探测估计器需要的）而不是醒来次数。没有探测时仍用普通定时器，不增加空闲唤醒。`FARWING_PROBE_PACING=0` 切回原来的发送方式。

**同时修正的自动画质**：探测修好后，码率在开播头一两秒就能涨上去，这时还没有丢包数据，自动画质（原条件是“当前没有丢包就升档”）会立即升到 2304×1440 甚至 2560×1600，在随机丢包的链路上画面越大、要等修复的帧越多。改为至少观察 3 次（约 3 秒）、且这段时间里没有测到过丢包才升档；降档不受影响。

**试过但没有采用**：

- 丢包维持码率时每 5 秒加探一次：探测本身仍然发不完整，首次连接没有明显改善，瓶颈加丢包下两次掉到 30 fps，撤回。
- 第一版补发不限量（晚醒时把欠下的字节一次发完，可达几十 KB）：成串冲击瓶颈队列和接收缓冲，无损下每场多出关键帧、瓶颈加丢包且记得 8 Mbps 时关键帧 1 → 11，改为最多补两步。

| 随机丢包约 2 %，记得 8 Mbps | 58.9 / 58.9 | 2 / 1 | 36.1 / 37.1、64.2 / 68.6 ms | 85 / 85 ms |
| 丢包加瓶颈，记得 8 Mbps | 55.2 / 57.0 | 8 / 19 | 50.0 / 50.4、119.8 / 93.8 ms | 123 / 105 ms |

重度丢包下改善最大（原来卡在约 1.6 Mbps、30 fps）。代价来自更高的码率与分辨率：约 2 % 丢包时码率是原来的数倍，每帧的包更多，等修复的帧也更多，延迟 p95 多约 6 ms（卡顿与最大延迟反而更少）；无损下几秒内升到原生分辨率 2560×1600（原来多数停在 1728×1080），延迟 p95 多约 0.8 ms——实际使用中观看端记得上次的档位，局域网上原来也会跑这一档；瓶颈加丢包时最长间隔多约 20 ms。按你的决定默认启用。

**与基线的标准回归**（§19 的场景，基线程序与本轮程序交替，各 4 次）：无丢包 H.264 / H.265 / AV1、整帧丢失、播放窗口的无丢包与整帧丢失：帧数、帧间隔持平；本轮程序收到的数据量是基线的 2–4 倍，并在几秒内升到原生分辨率（每次多 2 个关键帧，即两次升档）。注意 §19 这些场景的丢包与限速注入在主控收包处，被控的拥塞控制看不到（反馈在注入之前生成）：探测修好后被控把码率开到 10 Mbps 左右，于是“可修复丢包”两项比基线差——无窗口解码 ≥100 ms 间隔 22–23 对 13–16 次，播放窗口延迟 p95 75–93 对 65–66 ms、小卡顿 23–27 对 9–16 次。真实网络里被控能从反馈看到丢包，对应的结果是上表的“随机丢包约 2 %”（小卡顿更少、p95 多约 6 ms）。第 2 次运行时测试动画窗口没有在更新（被控日志每 5 秒多达 150 次“没有新画面”，基线与本轮的其余各次都没有），之后把动画窗口设为置顶重跑了第 3、4 次，结果如上。

**另外两项的结论**：

- 无窗口解码在丢包下 ≥100 ms 间隔比基线多（§20）：每次运行的间隔数与这次运行收到的数据量走同一条趋势线（数据量越少、间隔越多，基线与新版的点都在线上），是码率轨迹的差异，不是恢复时机的问题。
- “FEC 补回的包不再重传”评估后不做：多余的重传最多等于 FEC 补回的包数（约 2 % 丢包下每 40 秒 815 个、约 6 % 下 1960 个），约占带宽 1–3 %；推迟重传请求会在 FEC 补不回来时增加延迟，得不偿失。

## 22. 性能剖析（2026-10-19）

**方法**：被控与播放窗口在同一台机器上，2560×1600、60 fps、H.264，无损，画面持续运动。进程级用 PowerShell 统计 CPU 时间、内存、句柄和显卡各引擎占用；线程级按线程名（`GetThreadDescription`）汇总 CPU；函数级用 Windows 调试器 `cdb` 非侵入式附加，每次抓下所有线程的调用栈，抓 250 次，只统计正在运行（不在等待）的线程（脚本 `temp/reg/perfsample.ps1`、`perfthreads.ps1`、`stacksample.sh`、`stackagg.py`）。

**修复前的基准**（单核百分比）：被控约 22–31 %（tokio 网络线程约 15 %、采集线程约 5 %、`capture-inventory` 1.5 %），工作集约 130 MB；播放窗口约 21 %，工作集约 210 MB；显卡编码约 13 %、解码约 5 %。与基线程序在同一分辨率下相比，CPU 差别在测量波动之内，播放窗口的内存还略少。

**热点：显示器清单**。被控正在运行的采样里约一半（69 次中的 34 次）落在每秒一次的显示器清单读取：逐个读取每条显示路径的设备信息（`DisplayConfigGetDeviceInfo`），再用 `EnumDisplaySettings` 把显示器支持的全部模式枚举一遍——每个模式一次驱动调用；采集线程每秒也读一次屏幕列表。改为：先用便宜的 `QueryDisplayConfig` 结果算出配置指纹，指纹不变时复用上次读到的显示器信息与模式列表，最长 10 秒强制重读；DPI 每次照常读取（缩放变化不受影响）；改分辨率前的模式校验仍直接读取。同一场景各 3 次：被控 CPU 22.2–30.9 % → 17.6–18.2 %，tokio 网络线程约 15 % → 8 %，`capture-inventory` 1.5 % → 0.2 %；播放窗口不受影响。

**播放窗口**：250 次快照里只有 29 次线程在运行，分散在界面主循环（winit 消息处理与重绘）、网络线程、解码与声音线程，没有集中的热点。远端光标只在形状真正变化时重新生成（相同图像会复用），开销正常。

**线程数**：被控约 184 个、播放窗口约 228 个线程，其中 134 / 188 个是 NVIDIA 显示驱动为每个 D3D 设备建立的内部线程（栈底 `nvwgf2umx`），整个会话中数量稳定，不是泄漏。要减少需要让采集、编码、呈现等模块共用 D3D 设备，属于结构性改动，暂不处理。

## 23. 连接建立与首帧时间（2026-10-19）

**测量方法**：主控与被控在同一台机器上，主控像设备中心那样经在线连接发起会话（`FARWING_SIGNAL_PRESENCE=wait`），被控画面持续运动，每次连接 9 秒后关闭；从主控日志 `creating server session` 起，按两端日志里的阶段计时到主控 `first picture presented`（新加的一行日志：第一张画面真正上屏）。脚本 `temp/reg/startrun.sh`、`startagg.py`。

**改动前各阶段**（中位数，ms）：主控探测本机解码能力 112 → 被控收到会话 112 → 被控准备好连接 178 → 连通 268 → 被控采集就绪 360 → 编码器就绪 434 → 第一帧 486 → 主控解码器打开 501 → 交换链 555 → 上屏 558。逐段加计时后找到的耗时：

- 主控每次连接都重新探测本机所有显卡能解哪些格式（每张卡建一个设备、逐个格式询问驱动），约 110 ms，而且在发出会话请求之前。
- 被控每次会话结束时显卡驱动的用户态部分随最后一个 D3D 设备一起卸载，下一次会话打开采集时重新加载，130–210 ms；之后编码设备（25 ms）、纹理交接用的 D3D12 设备（45–80 ms）也是串行创建的。
- 被控第一次截屏有一半概率只拿到鼠标更新（新建的桌面复制对象常见），原代码要等一整个帧间隔再试。
- 主控的视频交换链与渲染设备等第一张画面解码出来之后才建。

**改动**：

- 主控把解码能力探测的结果按显卡集合（适配器 LUID 列表）记住，并在设备中心或 `connect` 启动时就在后台探测（设备中心随开机自启到托盘时推迟 30 秒）；显卡或驱动变化（驱动更新会让适配器换 LUID）后重新探测，什么都没探测到时不记住。屏幕的 HDR 等信息仍在每次连接时读取。
- 被控在会话通过认证、确定要采集的屏幕后，立即在后台线程为该屏幕所在（及其渲染）显卡建一个 D3D11 设备：驱动的加载与对端连接的建立并行；这个设备留给编码器使用（编码器取用时若还在创建就等它，最多 2 秒）；需要 D3D12 交接时同时建好 D3D12 设备。没被取用的在 10 秒后释放，空闲时不多占内存。
- 被控采集在拿到第一张桌面画面之前，没有画面时立即再等下一次桌面更新（最多 3 次），不再等一个帧间隔。
- 主控的播放窗口建好后立即在解码器所在显卡上建渲染设备与交换链，与第一帧的解码并行；第一帧若来自别的显卡或是软件解码，先释放预建的再按原方式建（一个窗口只能有一个交换链）。

**试过但没有采用**：采集也直接用预热好的设备——采集就绪早了 45 ms，但编码设备因此晚建，第一帧只早 3 ms，还要多占一个设备；预热时先开一次 NVENC 会话或初始化一个编码器——测得 NVENC 首次初始化（约 28 ms）是每个设备各付一次，只能在编码器自己的设备上做，而在那个设备上做会与编码器争用同一个上下文（试验版本因此卡死），已撤回。

**结果**（同一台机器、同一画面，改动前 / 后交替各 10 次，中位数与范围）：

| 场景 | 改动前 | 改动后 |
|---|---|---|
| 无丢包，到第一张画面上屏 | 558 ms（529–678） | **318 ms**（295–390） |
| 约 2 % 随机丢包、单程 30 ms（各 5 次） | 698 ms | **464 ms** |

改动后各阶段：会话请求 6 ms 发出，被控连通 174 ms，采集就绪 207 ms，第一帧 250 ms，上屏 318 ms。现在第一帧的下限是被控显卡驱动的加载（130–180 ms，从收到会话算起）。被控建立对端连接的 65–88 ms 几乎都花在读取显示器清单（`QDC_ALL_PATHS` 在本机有 333 条路径、主屏 385 个显示模式），但它与驱动加载并行、不在关键路径上，没有改。

**不倒退检查**（改动前 / 后的程序交替运行 §19 的标准场景，观看端每次都从档位 2 开始，以免记住的档位在两组之间传递）：无窗口解码的无丢包 H.264 / H.265 / AV1 各 5 次，帧间隔 p99 与最大值的范围重叠（H.264 最大 60.8 / 62.1 ms），帧数因起步更快多 10–12 帧；限速 20 Mbps、整帧丢失、播放窗口的无丢包 / 可修复丢包 / 整帧丢失各 2 次：停顿、帧间隔、延迟、渲染帧率持平或更好（可修复丢包的播放窗口未显示的帧 50 → 27）；无窗口解码的可修复丢包（丢包注入在主控收包处）冻结 1.3 / 1.6 s，范围重叠，与 §19 所述的波动相当。被控与观看端在会话第 4、15、30 秒和结束后 15 秒的线程数与内存与改动前相同（被控约 187 个线程、私有内存约 290 MB，结束后回到约 15 MB；观看端约 235 个线程、约 260 MB）。第一版在观看端启动时把软件 AV1 支持也一并提前探测，多建了一个设备，观看端工作集多 6–11 MB；改为只提前探测硬件解码（软件 AV1 仍在连接接受 AV1 时才探测）后与改动前相同。

## 24. 减少显卡设备与内存（2026-10-19）

**每个设备的代价**（本机 NVIDIA 驱动，小程序逐个创建后测）：第一个 D3D11 设备加载驱动，约 30 个线程、48 MB 私有内存；之后每多一个 D3D11 设备多约 29 个驱动线程、15 MB 私有内存（关闭驱动内部多线程优化只少 2 个线程，不带视频支持标志也一样）；一个 D3D12 设备多 7 个线程、约 22 MB 私有内存和 17–29 MB 工作集。

**被控**：NVENC 用自己的 D3D11 设备编码（与采集设备分开，采集端的转换与编码不争用同一个上下文），采集到的画面经两块共享纹理和 GPU fence 交给编码设备。这两块共享纹理原来由一个专门的 D3D12 设备分配，它在整个会话中一直存在。改为由采集设备直接创建共享纹理（`D3D11_RESOURCE_MISC_SHARED | SHARED_NTHANDLE`）和共享 fence（`D3D11_FENCE_FLAG_SHARED`），编码设备打开同一句柄；拷贝、信号与等待的顺序不变。D3D12 现在只用于两块显卡之间的交接，会话预热也只在这种情况下创建它。

会话中被控进程（第 4、15、30 秒，各 2 次）：线程 188 → 180，工作集 134 → 120 MB，私有内存 295 → 275 MB；会话结束后与空闲时不变。观看画面正确（截图核对），日志仍是 `same-adapter shared texture with GPU fences`，没有退回 CPU 中转。

**不倒退检查**（改动前 / 后交替，观看端固定从档位 2 开始）：无窗口解码的无丢包 H.264 / H.265 / AV1、限速 20 Mbps、整帧丢失、可修复丢包与播放窗口的无丢包 / 整帧丢失各 5 次，可修复丢包的播放窗口 2 次：所有指标的范围都重叠（帧间隔、停顿、冻结、延迟、渲染帧率），可修复丢包下改动后略好（冻结 1.83 → 1.54 s）。被控每 5 秒的统计中，交接耗时（平均 0.08 ms）、编码耗时（平均 2.75 ms）与每帧总耗时（平均 3.4 ms）两者相同。

**没有改的**：观看端约有三个 D3D11 设备（解码、界面、视频呈现），界面与视频呈现分开是为了互不阻塞（界面的 `Present` 会持有设备锁，合用会让视频线程等待），解码设备也不与呈现共用，这些合并会影响流畅性，不做；被控的采集与编码设备分开同理。

## 25. 随机丢包下的延迟（2026-10-19，试验，未改默认）

**背景**：§21 修好探测后，约 2 % 随机丢包的首次连接中延迟 p95 多约 6 ms（40.9 / 34.7 ms）：码率更高、每帧的包更多，等重传的帧也更多。

**分析**：观看端发现缺包时立即发 NACK（与 libwebrtc 的 NackRequester 相同），被控的重传在发送队列中先于画面发出，这条路径上没有可省的等待；能做的是让 FEC 补回更多的包。2 % 丢包下 FEC 每次只补回约 180 个包（同一次约 1800 个重传包，其中一部分是带宽探测包），因为 FEC 只用画面用剩的带宽（估计的 60 % 以内）。

**试验**（同一程序用环境变量切换，被控端链路模拟，画面持续运动，观看端每次从档位 2 开始，各 4 次，中位数，基准 / 试验）：

- F1，FEC 上限从估计的 60 % 提到 80 %（仍低于拥塞控制停止探测的 85 %）：首次连接的随机丢包 p95 39.1 / 34.8 ms，FEC 补回 183 / 295 个包；但从 10 Mbps 起步（记得上次码率）的随机丢包 p95 36.6 / 48.0 ms、未显示的帧 7.5 / 16.5，丢包加 6 Mbps 瓶颈有一次只有 33 fps。
- F2，每帧至少一个修复包，FEC 占用从编码器码率中扣除：丢包加瓶颈明显更好（p95 51.6 / 43.0 ms，小卡顿 8.5 / 3.5，最大延迟 87.7 / 67.8 ms），但首次连接的随机丢包帧率 59.8 / 56.6、未显示的帧 9.5 / 15.0，只限速 6 Mbps 有一次 44 fps。

两种都让某个场景变差，按"不能让其他场景倒退"的要求都没有采用，默认行为不变，试验代码已撤回。另外，同一程序、同一设置下 p95 在 35–44 ms 之间随运行变化（取决于这次码率涨到多高、多少帧赶上丢包），6 ms 的差别接近单次运行的波动。可能的后续方向：只在丢包是随机的（延迟不涨）而且码率已到档位上限时加大 FEC，需要先能可靠地区分这两种情况。

## 26. 内存去向、首帧与重连（2026-10-19）

**内存去向**（会话中用 `cdb` 非侵入附加列出全部已提交内存，另用小工具按页统计常驻集 `temp/enc/wsmap`）：

- 观看端与设备中心：各有两份约 18.8 MB 的完整中文字体（`msyh.ttc`）——我们读进内存一份，egui 每次建字体时再把"自有"字体数据复制一份。改为字体文件只做一次内存映射（页面属于文件、按需读入，不算进程私有内存），内置字体解压一次后常驻并以静态数据交给 egui，不再复制。观看端会话中私有常驻 111.6 → 70.9 MB；设备中心（在托盘待机时私有常驻约 73 MB，其中 37.6 MB 是这两份字体）同样受益（设备中心只能从安装位置运行，本机未单独测量）。字体加载日志 `installed system CJK font`，中文显示不变。
- 被控：私有提交约 240 MB，但常驻只有约 70–80 MB：NVIDIA 驱动为每个普通 D3D11 纹理在系统内存里预留与纹理一样大的空间（2560×1600 纹理各 16.25 MB，纹理释放后也不归还，直到设备销毁），这部分不常驻，任务管理器的"内存"一列看不到；另有每个设备约 8–32 MB 的写合并缓冲（驱动的上传环）。都属驱动内部，不改。
- 观看端其余主要是驱动的写合并缓冲（三个设备）与驱动放在进程堆里的分配，同样不改。

**首帧再快**：

- 被控会话预热时，在给编码器准备的设备上先建一次小编码器再释放：NVENC 在每个设备上的第一次初始化要 25–30 ms（同一设备之后只要几毫秒），现在在等待驱动加载与连接期间完成；这一步完成前设备不会交给编码器（编码器取用时会等）。
- 建立对端连接时读取显示器清单要 60–85 ms（本机全部显示路径 333 条、主屏 385 个模式），而且在发出应答之前。会话开始时改为使用配置未变时最近 10 分钟内读到的结果，会话的第一次定期读取（1 秒内）按原来的 10 秒规则重新读取，所以换显示器等变化仍在原来的时限内反映（§31.3）。

**重连更快**：会话结束时（编码器、采集都已释放），用刚结束的会话的设备撑住驱动、另建一个新设备并照样做好 NVENC 初始化，保留 60 秒；期间再次连接直接取用。不保留用过的设备：驱动在设备销毁前不归还它释放过的纹理的内存（实测保留用过的设备时进程私有提交多约 150 MB）。

**结果**（中位数，ms，从主控开始建会话到第一张画面上屏）：

| 场景 | 改动前 | 改动后 |
|---|---|---|
| 被控刚启动后的第一次连接（每次重启被控，各 6–8 次） | 375 | **348** |
| 一分钟内再次连接（同一被控进程，第 2–6 次） | 314 | **218** |

重连时被控在 25 ms 内就准备好应答（原 86 ms），113 ms 连通（原 175），142 ms 发出第一帧（原 246）。

**代价**：会话结束后的 60 秒内被控多占内存——工作集 58 → 96 MB、私有提交 16 → 117 MB、线程 36 → 93；60 秒后与原来相同（工作集 59 MB、私有 18 MB）。会话中的内存与线程不变。

**不倒退检查**（改动前 / 后交替；每组里被控在同一进程中连续接受多次会话，所以第 2 次起用的是保留下来的设备）：无窗口解码的无丢包 H.264 / H.265 / AV1 与播放窗口无丢包各 3 次，限速、整帧丢失、可修复丢包与播放窗口整帧丢失各 6 次：所有指标的范围都重叠；整帧丢失与限速场景改动后略好（冻结 1.04 → 0.93 s、0.22 → 0.18 s），可修复丢包冻结 1.41 / 1.64 s、帧间隔 p99 93.9 / 94.8 ms（范围重叠，这一场景丢包注入在主控处，与被控的这些改动无关）。

## 27. 高分辨率高帧率剖析（2026-10-19）

**方法**：本机屏幕 2560×1600、165 Hz（没有 4K 屏，未用虚拟显示器以免改动桌面布局），原生分辨率档位（`--dev-auto-quality 4`），H.264，测试动画窗口放大到 1200×800（逻辑像素，约占屏幕一半）持续运动；进程级 CPU / 内存 / 显卡引擎占用（`temp/reg/perfrun2.sh`）、按线程名的 CPU、`cdb` 调用栈抽样各 150 次。

| | 60 fps | 144 fps |
|---|---|---|
| 实际渲染帧率 | 59.8 | 143.9 |
| 本机延迟 p95 / 渲染间隔 p95 | 1.6 / 17.6 ms | 1.3 / 8.1 ms |
| 被控 CPU（单核 %） | 11.8 | 21.2（网络线程 12.8、采集编码线程 5.5） |
| 观看端 CPU（单核 %） | 17.3 | 18.6 |
| 显卡：编码 / 解码 / 3D | 11 / 4.3 / 3.8+1.7 % | 26 / 10 / 9+4 % |

144 fps 下没有卡顿，丢弃的呈现帧 6 个（60 fps 时 3 个）。被控每帧的网络处理约 0.9 ms CPU（打包、加密、发送），采集线程的大部分"运行"样本其实停在桌面复制等待下一帧的内核调用里；观看端的样本分散在收包解密、界面消息与呈现，没有集中的热点。唯一可见的小项是被控在桌面无声时仍以不带 DTX 的方式编码桌面声音（约占忙碌样本的 9%，约单核 2%），改动会影响声音起播，暂不处理。结论：这一分辨率与帧率下两端都有足够余量，不需要改动；真正的 4K 144 Hz 需要在有 4K 高刷屏的机器上测（清单 32.10）。

## 28. 观看端首帧（2026-10-20）

**逐段计时**（观看端，从收到第一个视频包算起）：等齐第一帧并打开解码器 11–15 ms；第一次硬解提交 34 ms（之后每帧约 1 ms，同一设备上换分辨率重建解码器后的第一次也只要 5–6 ms：慢的是硬解在一个设备上的第一次初始化）；视频呈现在解码器打开后才开始建，其中渲染设备约 22 ms、交换链约 3–6 ms、着色器约 1 ms。

**改动**：播放窗口一建好（连接还在进行），就在后台线程里用内置的 H.264 编码器生成一张 64×64 的小画面，在解码器将要使用的设备上硬解一次；同时为视频呈现建好渲染设备，播放开始时直接取用（不可用时按原方式现建）。

**结果**（同一被控进程中连续连接，中位数）：第一个视频包到上屏 69 → 33 ms；一分钟内再次连接到上屏 210 → 164 ms，被控刚启动后的第一次 352 → 329 ms。会话中观看端内存与线程不变。

**不倒退检查**（改动前 / 后交替各 3 次，观看端固定从档位 2 开始）：播放窗口的无丢包与整帧丢失：丢弃的呈现帧 3 → 1（开头不再丢），其余指标相同；无窗口解码各场景（不经过播放窗口，这次的改动不涉及）范围重叠或互有高低，属于测量波动。

## 29. 空闲唤醒（2026-10-20）

**方法**：没有人连接时，用性能计数器统计每个线程每秒的上下文切换次数（即被唤醒的次数，`temp/reg/ctxsw.ps1`），对唤醒最多的线程用 `cdb` 加符号查看它在等什么。

**改动前**：托盘里的设备中心约 137 次/秒，其中一个线程 69 次/秒；服务启动的常驻被控进程约 103 次/秒（一个线程 96 次/秒）；不经服务的命令行被控约 56 次/秒。设备中心、服务和常驻被控之间的命名管道在等待"下一个连接"或"下一条请求"时，每 5 ms 醒来一次看是否该退出（Windows 计时精度下约 64 次/秒），而这些连接在空闲时一直开着。

**改动**：只在两类等待上把这个检查间隔改为 100 ms——管道监听等待新连接，以及只负责应答请求的长连接（服务的管理连接、常驻被控的会话通道、设备中心的用户后台）。请求或连接一到仍会立即唤醒，影响的只是退出、取消时最多多等约 0.1 秒。会话中的输入、采集等管道循环保持原来的 5 ms。

**结果**（各测 15 秒）：托盘设备中心 137 → 78 次/秒，常驻被控 103 → 28 次/秒；服务进程以 SYSTEM 身份运行，本机无法读取它的线程计数，它的管理连接用的是同一处改动。改动后在本机通过服务连接被控、播放正常，设备中心在线状态正常。设备中心剩下的唤醒主要来自它每 0.25–0.5 秒一次的状态轮询（向服务取快照、读取保存的登录），要再减少需要把设备中心与服务之间改成服务主动推送，属于结构改动，暂不做。

## 30. 网页端观看的首帧与流畅（2026-10-20）

**方法**：本机 Chrome（由开发者工具驱动）打开生产构建的网页（`vite preview`，接口代理到测试服务器），每次访问用一个新的同源页面框打开 `/visit`、填访问码提交；浏览器端记录加入完成、`session.start`、第一个视频包、`loadeddata`（第一张画面可显示），并每 0.25 秒读一次 `getStats`；被控日志按时刻对齐。被控上持续播放测试动画。

**找到的耗时**：

- 提交后约 20 ms 花在访问码 SPAKE2 的第一次计算上：要先建立基点的倍数表，之后每次只要约 1.5 ms。
- 被控在连接建好之后才建编码设备和编码器（约 10 ms）；连通后还要等对方的 HELLO 应答，采集线程每 20 ms 才看一次能不能开始。从连通到发出第一帧中位 35 ms。
- 网页每次都从自动画质的第 2 档开始（本机 1728×1080），约 3.3 秒、5.3 秒时各升一档；每次升档都重建编码器、发关键帧，浏览器的解码器也跟着重配。
- 在菜单里选过编码的访客（选择存在浏览器里）：被控先按自己的选择（AV1）建编码器、发出第一帧，浏览器拿到被控能力后才发设置改成所选编码，被控再建一次编码器，Chrome 再换一次解码器。
- 没有改的：Chrome 连通后 0.2–0.4 秒会把选中的候选地址换成另一对（本机先选 IPv4 或链路本地地址，再换成 IPv6），被控按路径变化把带宽估计重置为起始码率，这与 libwebrtc 发送端的处理相同；被控收到 offer 后建立 ICE 代理约 10 ms（大部分是 mDNS），候选地址约 25 ms 后发出。测试服务器只监听 127.0.0.1、地址却写 `localhost`，被控到服务器的 HTTP 连接空闲过期后重建时先试 `::1`，约 300 ms 后才改用 IPv4，偶尔让"加入"慢 300 ms；这是测试环境的配置问题。

**改动**：

- 网页：访问页一打开就在后台建好 SPAKE2 的倍数表，访客输入访问码的时间里就完成了。
- 网页：记住每台被控上次报告的自动画质档位（只在自动画质下记），下次从那一档开始，和原生客户端一样。
- 网页、被控、服务端协议：`session.start` 的画面参数加了 `codec`（0 表示由被控选择）。网页把菜单里选过的编码放进去；双方都支持这种编码时，被控从一开始就用它，换屏幕重新开始采集时也保留；不支持时照旧由被控选择。原生客户端填 0，行为不变。
- 被控：采集已经就绪、连接还在建立时，就用第一张画面建好编码设备和编码器；连接可以发画面时（对端应答了 HELLO、屏幕信息已发出）立即唤醒采集线程，不再最多等 20 ms。

**结果**（同一台机器，改动前 / 后交替；被控刚启动后的第一次单列）：

| 场景 | 改动前 | 改动后 |
|---|---|---|
| 网页访问，提交到第一张画面（各 10 次中位数） | 260 ms | **229 ms** |
| 其中：提交到加入完成 | 50 ms | 37 ms |
| 其中：被控连通到发出第一帧 | 35 ms | 12 ms |
| 网页访问，菜单里选过 H.264（各 5 次） | 260 ms | **214 ms** |
| 被控刚启动后的第一次网页访问（各 2 次） | 326 ms | 332 ms（持平） |
| 原生客户端，连接到第一张画面上屏（各 10 次） | 165 ms | 158 ms |
| 原生客户端，被控连通到发出第一帧 | 34 ms | 9 ms |

流畅：同一台被控第二次起的网页访问，一开始就是原始分辨率（0.33 秒，改动前约 5.3 秒才升到），7 秒内只有 1 个关键帧（改动前 3 个），丢帧和卡顿都是 0；选过 H.265、AV1 的访问也都从所选编码开始、只有 1 个关键帧。原生客户端的第一帧更早到达时，观看端正忙于连接握手，从收到第一个视频包到上屏由 27 ms 变成 37 ms，所以上屏只早了约 7 ms；观看端仍有优化空间。

**不倒退检查**（改动前 / 后交替各 3 次，§19 的无丢包场景）：无窗口解码 H.264 / H.265 / AV1 的每秒帧数相同（AV1 的总帧数少 2–3 帧，是统计窗口长度不同：30.10 秒对 30.04 秒），帧间隔 p99 相同，最大间隔范围重叠（H.265 57.6 → 49.5 ms，AV1 56.5 → 61.7 ms，属于波动），关键帧数相同；播放窗口的渲染帧率、帧间隔、延迟持平，未显示的帧 1 → 0。改动只涉及会话开始阶段与编码选择，会话中的采集、编码、发送路径没有变化。

## 31. 连接建立、第一帧与弱网首帧（2026-10-20）

**方法**：同 §23（原生客户端经在线连接发起，`temp/reg/startrun.sh`、`startagg.py`），加上被控与观看端的详细日志按时刻对齐；网页端同 §30，但两次访问间隔 15 秒（更接近实际：被控的显示器清单缓存只保留 10 秒）。弱网用被控端的模拟链路（`FARWING_HOST_LINK`，只作用于视频包）。按要求只做简短测量：每组 4–5 次（去掉被控刚启动后的第一次）。

**找到的耗时**（改动前，从主控发起会话算起）：

- 被控收到 offer 后建 ICE 代理要先打开 mDNS（在每块网卡上加入组播组）约 10 ms，主控生成 offer 时同样如此，都在关键路径上；mDNS 只用来解析对方的 `.local` 候选地址。
- ICE 检查每 48 ms 才发一次，而且第一次常落在发不出去的地址对上（本机有 VPN 的链路本地地址，"网络不可达"立即失败），这一次仍占掉一个间隔；检查定时又与上次发出的时刻错开，实际间隔常到 60–96 ms。连通（DTLS 完成）中位约 110 ms。
- ICE 按 libwebrtc 的网卡排序，把 Windows 报告为"未知类型"的网卡（Teredo、TUN 虚拟网卡）排在以太网和 Wi‑Fi 前面，对方会先检查这些多半不通的地址。
- 被控的采集要等到 SDP 协商完才开始打开（约 40 ms），而采集线程在会话准备阶段就已经建好了。
- 连接建好、握手完成后，被控第一次发屏幕列表前，周期性的显示器清单读取会先做一次完整读取（上次完整读取超过 10 秒时 40–80 ms），屏幕列表发不出去，第一帧也就等着；实际使用中两次连接通常隔得更久，所以几乎每次都会碰到。
- 观看端在第一帧上打开解码器后，解码器池因为还不知道格式，马上又用同样的配置建了一个新的（约 5–9 ms）。

**改动**：

- ICE（内置的 webrtc-ice）：mDNS 连接改为后台打开，建代理和生成 offer / answer 不再等它；网卡按网络开销排序（以太网、Wi‑Fi、其他、蜂窝、VPN），未知类型的隧道网卡排到真实网卡之后（仍然提供，只是后试）；没能发出的检查不占用发送间隔，立即检查下一对（连续最多 4 次，避免无网络时空转）；下一次检查安排在上次发出后正好一个间隔。
- 被控：采集线程一启动就打开采集，不再等 SDP 协商；第一次周期性显示器清单读取推迟到会话开始 1 秒后（会话准备时刚读过）。
- 观看端：第一帧时按可见尺寸打开解码器，解码器池直接沿用，不再立即重建；会话可以播放时立即唤醒播放窗口（原来最多等 33 ms 的界面刷新）。
- 服务端：接受的连接设置 TCP_NODELAY（实时通道的小消息不再可能等对方的延迟确认）；本机测试经过 Vite 代理，测不出差别。

**结果**（原生客户端，改动前 = 上一轮版本，改动后为本轮版本，中位数）：

| 阶段（从发起会话算起） | 改动前 | 改动后 |
|---|---|---|
| 被控连通 | 110 ms | 43 ms |
| 被控发出第一帧 | 135 ms | 77 ms |
| 第一张画面上屏 | **159 ms** | **105 ms** |
| 约 2 % 随机丢包、单程 40 ms：第一张画面 | 293 ms | 214 ms |
| 限速 5 Mbps、单程 40 ms：第一张画面 | 675 ms | 252 ms |

网页访问（间隔 15 秒，各 4 次）：提交到第一张画面 243 → 198 ms。限速时改动前常因解码器在第一帧上重建、再加上关键帧请求，要多传一到几个关键帧；改动后少了这一步。

**没有改的**：Chrome 连通后 0.2–0.4 秒会换一次候选地址对（先选最先能用的，再换成优先级更高的），被控像对待任何路径变化一样把带宽估计重置为起始码率，再由探测在几百毫秒内恢复；这与 libwebrtc 发送端的做法一致，没有改。观看端从解码器打开到交换链建好还要 15–20 ms（播放窗口与交换链在第一帧之后才建），提前建需要改动连接界面与播放界面的切换，留待以后。

**不倒退检查**（§19 的无丢包场景，改动前 / 后交替各 2 次）：无窗口解码 H.264 / H.265 / AV1 的每秒帧数、帧间隔 p99、关键帧数相同；最大帧间隔 H.264 53.7 → 49.1 ms、H.265 44.7 → 49.2 ms、AV1 63.7 → 76.3 ms（范围 63–90），单个场景的最大值波动很大（上一轮同一指标 H.265 是 57.6 → 49.5 ms），改动也不涉及会话中的采集、编码、发送与解码路径；播放窗口的渲染帧率、帧间隔、延迟持平，未显示的帧 1 → 0。单元测试通过。

## 33. 观看端首帧、重启后的硬件编码、重连内存与本机补测（2026-10-20）

### 观看端首帧

播放窗口的视频子窗口改为在连接阶段就建好（先隐藏），交换链与显示设备一起在预热线程中建好；开始播放时显示这个窗口并直接使用这条交换链。没用上的交换链（软件解码、窗口不同）在建新的之前释放并刷新。原生客户端经在线连接各 10 次（`startrun.sh`，新旧交替），中位数：

|---|---|---|
| 收到第一个视频包到第一张画面上屏 | 40 ms | 25 ms |
| 解码器打开到上屏 | 约 12 ms | 约 8 ms |
| 从发起会话到上屏 | 501 / 496 ms | 494 / 487 ms |

软件解码（`--hardware-decode false`）与被控重启后的自动重连都正常出画面；重连时新窗口同样提前建好交换链。

### 重启后被控只能用软件编码（已修复）

本轮测试中发现：被控把编码能力检查结果存在 `cache/encoder-probe.json`，检查的依据按显卡的 PCI 身份记录（适配器 LUID 每次开机都会变），但结果里每个编码器仍带着当时的 LUID。开机后 LUID 变了，所有硬件编码器都因“采集适配器已移除”打不开，改用软件 H.264。开发机今天重启后，已安装的后台服务被控在日志中记录了 46 次失败、没有一次硬件编码。

修复：结果按适配器在依据中的位置保存，读取时换成当前的 LUID（旧格式的文件读不出来，会重新检查一次）。验证：把缓存中的 LUID 改成重启前的值来模拟重启，被控从磁盘恢复结果后直接用 NVENC 编码，没有失败记录。

### 多次重连后被控内存上涨（已修复）

被控为了让一分钟内的重连更快，会在会话结束后备好一个显卡设备，保留 60 秒。准备设备的线程把设备的上下文留到了 60 秒等待结束，导致会话用过的设备都跟着多留 60 秒。结果是一分钟内每连接一次，内存涨约 150 MB；6 次快速断开重连后被控进程的专用内存达到 1033 MB。上一轮之前的版本保持在约 177 MB。

修复后同样 6 次：274 MB，不随次数增长；断开 1 分钟后备用设备释放。重连到出画面的时间不变，从发起会话算起约 0.41–0.44 s。

### 网页端开头几秒的清晰度（研究，未改）

本机上，Chrome 连通约 0.25 秒后会从 169.254.x（虚拟网卡的链路本地地址）换到 IPv6 地址。被控把带宽估计从已测到的 5–20 Mbps 退回起始值 1.6–3 Mbps，随后它的指数探测（起始值的 3 倍、6 倍，再逐次翻倍）在几百毫秒内恢复。

试过一种改法：对“连通后 5 秒内、新旧路径都不经中继”的切换，在重置后加一次探测，探测码率为旧路径码率的 85%（与 GoogCC 在码率骤降后的探测相同）。在模拟链路（限速 20 Mbps、单程 25 ms）上新旧各测 4 次：

- 这次额外探测只在 1 次中触发。起始值的 6 倍已经超过旧码率的 85% 时，它不起作用；本机记住的起始码率较高时都属于这种情况。
- 触发的那次，之后估计超过了链路容量并被压低，画面在约 3 秒内都只有约 1.8 Mbps。不能排除和这次探测有关。

开头几秒的实际画质主要取决于编码档位的逐级上调（1080p 档 → 2K → 原生，各需几秒），而不是这次重置。因此没有保留这次改动。另外，Chrome 先选 169.254.x 地址是本机的特殊情况；两台机器之间这类地址通常不通，不会被选中。
