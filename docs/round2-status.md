## 2. 本机已验证（单机多 profile）

- 两位观看者同屏同参数共用一路编码，各 144 fps；参数不同时分组；组长离开约 120 ms 内由他人接替；关键帧对整组生效。
- 控制权：先到者获得、后到者被拒绝并看到持有者；释放后他人可获得；会话中收回授权约 2 ms 内释放并提示；持有者离开即释放。非持有者自动进入 1080p60 观影流并共用一路编码，持有者保留自己的设置与低延迟播放。
- 主控每秒上报接收端统计，被控据此决定解码帧率上限。
- 端口转发 TCP 单连接约 33–38 MB/s、4 连接并行全部校验一致；UDP 200/200。
- FILE v2 上传 / 下载文件夹（含空目录）全部一致；200 MiB 双向一致（约 26 MB/s）。
- 剪贴板（经 `dev clipboard`，主控为内存剪贴板）：文本、HTML、图片、24 MiB 数据、40 MiB 文件双向，多人会话中的手动获取。
- 诊断包传输与 SHA-256 校验。
- 被控进程重启后主控约 0.85 s 内恢复会话；直连会话恢复约 11 s（含被控重启）。
- 配对、错误配对码与锁定、已配对直连、本账号设备直连、直连协助码、局域网发现、直连与服务端参与者同会话、身份变化拒绝。
- 会话信令复用在线连接（与独立 WSS 的回退路径）。
- 客户端 lib 测试 157 项、服务端测试 78 项全部通过。
- 其余单机自测（恢复、文件、端口、诊断、直连、虚拟屏与超级屏、多人、输入注入等）的逐项结果与本轮修复见 [selftest-results.md](selftest-results.md)；剩余双机项目按环境分批整理在 [dual-machine-runsheet.md](dual-machine-runsheet.md)。

## 4. 已知限制

- ~~直连会话使用 UDP 端口段（默认 28890–28905），未使用单端口复用（内置 ICE 分配器不支持）~~ 2026-10-18 起所有直连会话共用 UDP 28890（`vendor/webrtc-ice/src/shared_port.rs`）；局域网发现使用 UDP 28889。
- ~~未启用后台服务时，切换“仅直连”需要重启程序。~~ 2026-10-18 起立即生效（设备中心按新设置重建被控端连接）。
- ~~“我的光标颜色”在下次连接时生效。~~ 2026-10-18 起连接中修改也立即生效（主控再发一次带 profile 的 HELLO）。
- ~~新参与者在收到首个画面设置前可能短暂使用自己的编码器，随后并入共享组~~（2026-10-18 起先跟随已有的组，设置到达后再定组）；编码路数达到上限时，另一屏幕或另一编码格式的参与者仍会新开编码器（记录警告）。
- ~~丢包网络上首次连接码率常常涨不上去（被控的探测包在 Windows 定时器下发不完整，探测没有结果）~~ 2026-10-19 修正（[selftest-results.md](selftest-results.md) §21）。
- ~~P5 的每帧 RS-FEC 实际没有发出：内置 WebRTC 库仍按旧编解码名称建立 FEC 流，两端都没有建立，弱网下只靠重传。~~ 2026-10-19 修正；现在只在测得丢包且有富余带宽时发送，网络正常或带宽被画面用满时不发（[selftest-results.md](selftest-results.md) §20）。
- 同一台机器上同时运行被控和多个高分辨率高帧率观看者时，CPU 竞争会让较慢的观看者丢帧更多（真实双机不存在此问题）。
